# راهنمای کندو

[English](GUIDE.md) · قبل از این: [کندو برای شما چه می‌کند](ONBOARDING.fa.md)

## ۱. چه چیزهایی لازم است

- **مغز:** یک ماشین لینوکس همیشه‌روشن با `systemd`، مثلاً یک سرور کوچک خانگی. ناظر آنجا اجرا می‌شود.
- **ماشینی که پشتش نشسته‌اید:** لپ‌تاپتان. اگر روشن بماند، می‌تواند خودش مغز هم باشد.
- `Claude Code`، یعنی `claude`، لاگین‌شده، با اشتراک یا کلید `API`.
- `GitHub CLI`، یعنی `gh`، لاگین‌شده با دسترسی `project`: دستور `gh auth refresh -s project`.
- `git` و `python` نسخه‌ی ۳.
- `SSH` از لپ‌تاپ به مغز، و از مغز به هر ماشینی که پروژه‌ای باید `in-place` روی آن اجرا شود.

چک: `claude --version`، `gh auth status` و `python3 --version` روی مغز جواب می‌دهند.

## ۲. نصب نسخه‌ی خصوصی خودتان

ریپوی عمومی یک قالب است. یک ریپوی خصوصی برای خودتان داشته باشید و ریپوی عمومی را `upstream` آن کنید، تا تسک‌ها و `PR`های کندوی شما خصوصی بمانند. روی مغز:

<div dir="ltr">

```
git clone https://github.com/25mordad/kandu.git kandu
cd kandu
git remote rename origin upstream
git remote set-url --push upstream DISABLED
gh repo create your-login/kandu-private --private --source=. --remote=origin --push
git config core.hooksPath .githooks
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

</div>

کندو همیشه از `.venv` خودش اجرا می‌شود، هیچ‌وقت از `Python` سیستم.

چک: `git remote -v` نشان می‌دهد `push` برای `upstream` روی `DISABLED` است.

## ۳. راه‌اندازی اول، با گفتگو

در پوشه‌ی `kandu` روی مغز، `Claude Code` را باز کنید و بزنید:

<div dir="ltr">

```
/kandu-setup
```

</div>

فرمی در کار نیست. کندو اول سیستمتان را می‌گردد و بعد یک فهرست شماره‌دار از چیزهایی که نتوانسته بفهمد می‌پرسد: مغز کجا اجرا می‌شود، چه ماشین‌هایی دارید، سقف مصرف، سازمان‌ها و حساب‌های `GitHub`، پیام‌ها و زبان، چند کارگر با هم کار کنند، پورت داشبورد، مدل هر نقش، و اینکه هر نقش چه کارهایی اجازه دارد.

در شروع دو جواب از همه مهم‌ترند:
- **سقف مصرف.** اگر اشتراکتان را با سشن‌های خودتان شریک هستید، حاشیه بگذارید، مثلاً ۷۰٪ برای پنجره‌ی پنج‌ساعته و ۶۰٪ برای هفته.
- **مجوزها.** بدون `permissions` هر ایجنت هر دستوری را می‌تواند اجرا کند. برای محدود کردنشان، از مجموعه‌ی کامنت‌شده در `config.example/kandu.example.yaml` شروع کنید.

خروجی‌اش `local/kandu.yaml` است، `local/.env` با یک توکن داشبورد که نشانش نمی‌دهد، و `local/private-words.txt`، یعنی واژه‌هایی که هیچ‌وقت نباید به ریپوی عمومی برسند. کل `local/` در `.gitignore` است.

چک: `.venv/bin/python -m kandu.config` قبول می‌شود و `.venv/bin/python -m kandu.doctor` هیچ `FAIL`ی نشان نمی‌دهد.

## ۴. اجرای داشبورد

<div dir="ltr">

```
.venv/bin/python -m kandu.timer --dashboard
```

</div>

این فقط داشبورد را اجرا می‌کند، به‌صورت یک سرویس کاربر که بعد از ری‌استارت دوباره بالا می‌آید. ناظر هنوز روشن نمی‌شود. روی سرور یک بار `loginctl enable-linger` را بزنید تا سرویس‌های کاربر موقع بوت بالا بیایند.

داشبورد روی `127.0.0.1:8790` در مغز گوش می‌دهد. از لپ‌تاپ یک تونل بزنید و `http://127.0.0.1:8790` را باز کنید:

<div dir="ltr">

```
ssh -N -L 127.0.0.1:8790:127.0.0.1:8790 server
```

</div>

خواندن روی همین آدرس آزاد است. توقف، ادامه و تأیید، بار اول `KANDU_DASHBOARD_TOKEN` را از `local/.env` می‌خواهند.

چک: صفحه باز می‌شود و مرغزار را خالی نشان می‌دهد.

## ۵. راه‌اندازی دیدبان روی ماشینی که پشتش نشسته‌اید

دیدبان راه حرف زدن با کندو از ماشین خودتان است: یک سشن `Claude Code` در نقش کنترل که تسک تعریف می‌کند، وضعیت را نشان می‌دهد و فرمان می‌دهد، و کد نمی‌نویسد. روی لپ‌تاپ، در یک کلون از کندو که `.venv` دارد:

<div dir="ltr">

```
mkdir -p local
cp config.example/didban.example.yaml local/didban.yaml
ln -s "$PWD/bin/didban" ~/.local/bin/didban
```

</div>

فایل `local/didban.yaml` را ویرایش کنید: `reach` اسم مستعار `SSH` مغز است و `install_dir` جایی که کندو آنجا نصب شده. بقیه‌ی چیزها از مغز خوانده می‌شود.

اگر پشت خود مغز نشسته‌اید می‌توانید این قدم را رد کنید، یا به‌جایش دیدبان را با دکمه‌اش در داشبورد باز کنید که آن را روی مغز با یک لینک `Remote Control` اجرا می‌کند.

چک: دستور `didban` یک سشن به اسم `Kandu` باز می‌کند و می‌گوید چه چیزهایی منتظرند.

## ۶. اضافه کردن اولین پروژه

برای اولین بار یک پروژه‌ی کوچک با تست واقعی انتخاب کنید. در دیدبان، یا در `Claude Code` روی مغز:

<div dir="ltr">

```
/kandu-add
```

</div>

کندو اول پروژه را می‌خواند، یعنی `remote`، دستور تست و روش دیپلوی، و بعد از شما تأیید می‌گیرد. بعضی جواب‌ها را هیچ‌وقت حدس نمی‌زند:
- **کجا اجرا شود:** `clone`، که کندو پروژه را در پوشه‌ی کاری خودش روی مغز کلون می‌کند، یا `in-place`، روی یک ماشین مشخص و در یک `git worktree` جدا، هیچ‌وقت در نسخه‌ی کاری خودتان.
- **نوع مرج:** فعلاً مرج خودکار را خاموش بگذارید.
- **دیپلوی:** `direct` یا `preview`، و آدرس نسخه‌ی زنده برای چک آخر. اگر نسخه‌ی زنده پشت لاگین است، آدرس را نگذارید.
- **بخش‌های ممنوع،** مثل `migration`ها یا پرداخت، و محل `secret`ها. کندو جای `secret` را نگه می‌دارد، هیچ‌وقت خود مقدارش را.

اگر پروژه بورد ندارد، کندو فقط وقتی شما بگویید یکی می‌سازد، با ستون‌های استاندارد: `Backlog`، `Technical debt`، `Ready`، `In progress`، `In review`، `Needs info`، `Needs split`، `Blocked` و `Done`.

چک: `.venv/bin/python -m kandu.doctor` نسخه‌ی پروژه، ابزار تست و ستون‌های بوردش را `OK` نشان می‌دهد.

## ۷. تعریف اولین تسک

در دیدبان چیزی را که می‌خواهید با زبان خودتان بگویید، به هر زبانی. یا `/kandu-task` را بزنید.

کندو اول کدی را که تسک به آن دست می‌زند می‌خواند و چک می‌کند این رفتار از قبل وجود نداشته باشد. برای تسک بزرگ یا مبهم سؤال‌های شماره‌دار می‌پرسد و برای هر کدام یک جواب پیشنهادی می‌دهد. بعد متن نهایی را نشانتان می‌دهد. تسک فقط بعد از تأیید شما ساخته می‌شود.

تسک روی `GitHub` به انگلیسی نوشته می‌شود، به هر زبانی که شما حرف بزنید، و همیشه همین بخش‌ها را دارد: هدف، رفتار فعلی، معیار قبول، روش تست، خارج از محدوده و `Blocked by`. کندو `Priority`، `Kind` و `Size` را خودش تعیین می‌کند. تسک `Large` قبل از رسیدن به بورد به برش‌ها شکسته می‌شود.

تسک خوب این‌طور است:
- می‌گوید نرم‌افزار باید چه کند، نه اینکه کدام فایل‌ها عوض شوند،
- هر معیار قبول جدا قابل چک است،
- بخش «خارج از محدوده» نمی‌گذارد کارگر تسک را بزرگ‌تر کند.

چک: تسک با لیبل `agent` در ستون `Backlog` بورد است.

## ۸. روشن کردن کندو

<div dir="ltr">

```
.venv/bin/python -m kandu.timer --enable
```

</div>

این تایمر و داشبورد را با هم روشن می‌کند. ناظر از حالا هر یک ساعت بیدار می‌شود، با `wake_every_minutes`. برای اینکه همین حالا یک دور شروع شود، در داشبورد **بیدار کردن ملکه** را بزنید. برای دیدن اینکه یک دور چه می‌کند، بدون اجرای هیچ ایجنتی:

<div dir="ltr">

```
.venv/bin/python -m kandu.supervisor --dry-run
```

</div>

تسک شما این مسیر را می‌رود:
1. **اندازه‌گیر** اندازه‌اش را می‌گیرد.
2. **ملکه** با سرعتی که پروژه می‌کشد آن را از `Backlog` به `Ready` می‌برد.
3. یک **کارگر** آن را در `worktree` خودش می‌سازد، اول تست، و روی یک شاخه‌ی `kandu/...` یک `PR` باز می‌کند.
4. یک **ریویوکننده‌ی تازه** `PR` را با معیارها می‌سنجد. کارگر چیزهایی را که پیدا شده حداکثر در دو دور فیکس می‌کند.
5. وقتی همه‌ی شرط‌های مرج روی کامیت ریویوشده برقرار باشند، اگر مرج خودکار روشن باشد `PR` **مرج** می‌شود، و اگر خاموش باشد منتظر شما می‌ماند.
6. کندو **دیپلوی** می‌کند و **چک زنده** را اجرا می‌کند. بعد تسک `Done` است.

یک دور وقتی تمام می‌شود که تسک‌ها تمام شوند، حدود ۵۰ دقیقه بگذرد، یا مصرف به سقف برسد. دور آرام هیچ توکنی خرج نمی‌کند.

## ۹. خواندن داشبورد

**مرغزار** اولین زبانه است. هر پروژه یک قطعه زمین است، هر تسک یک گل و هر ایجنتی که کار می‌کند یک زنبور: کارگر، بازبین، پیشاهنگ و اندازه‌گیر هر کدام ابزار خودشان را دارند. ملکه وقتی تصمیم می‌گیرد می‌درخشد و حرف می‌زند. هر وضعیت تسک گل خودش را دارد؛ اندازه‌ی گل اندازه‌ی تسک است و نشانه‌های زیرش تغییر سخت‌برگشت، برگشت از ریویو، برش، اندازه‌ی ناموجود یا سؤال باز را نشان می‌دهند. `PR`ی که منتظر شماست از همه بیشتر به چشم می‌آید. تسک‌های تمام‌شده تا پنج روز خانه‌های شانه‌ی زیر مرغزار را پر می‌کنند. علف‌های هرز تسک‌هایی هستند که در `Technical debt` کنار گذاشته شده‌اند. راهنمای کنار صفحه هر نشانه را وقتی پیدا می‌شود توضیح می‌دهد.

زنبورها یک تصویر بامزه‌اند، نه زیست‌شناسی: ملکه‌ی واقعی بر هیچ زنبوری نظارت نمی‌کند. ببینید [چرا زنبور](ONBOARDING.fa.md#چرا-زنبور).

**کارها** برای هر پروژه یک جدول دارد که جمع می‌شود و قابل جستجوست. چیزی که منتظر شماست اول می‌آید. با کلیک، تسک باز می‌شود، همراه با صفحه‌ی `PR` به زبان ساده: چه می‌کند، نتیجه‌ی ریویو، یک پیشنهاد یک‌خطی و توضیح هر یافته.

**مصرف روزانه** نشان می‌دهد هر روز چه کارهایی انجام شده و هر تسک چقدر توکن خرج کرده، به تفکیک مدل و نقش، به‌اضافه‌ی سشن‌های دیدبان و پروازهای آزاد.

**جریان زنده** هر فایلی را که ایجنت می‌خواند، هر دستور و تغییر، یادداشت‌های ریویوکننده و تصمیم‌های ناظر را همان لحظه نشان می‌دهد.

بالای صفحه: وضعیت ناظر، بیدار شدن بعدی، دلیل تمام شدن آخرین دور، نوارهای مصرف با خط سقف، و کنترل‌ها.

## ۱۰. وقتی کندو با شما کار دارد

کندو به‌جای حدس زدن می‌پرسد. اگر `Telegram` را تنظیم کرده باشید آنجا خبردار می‌شوید، و اول از همه روی داشبورد می‌بینیدشان:

| چه می‌بینید | یعنی چه | چه کار کنید |
|---|---|---|
| گل درخشان، یک `PR` منتظر | مرج خودکار خاموش است، یا تغییر سخت‌برگشت است | صفحه‌ی `PR` را بخوانید، بعد **تأیید و ادغام** را بزنید یا روی `GitHub` مرج کنید |
| `Needs split` | اندازه‌گیر تسک را بزرگ دیده و برش پیشنهاد داده | پیشنهاد را بخوانید و **قبول این شکستن** را بزنید، یا در دیدبان تغییرش دهید |
| `Needs info` | تسک برای شروع زیادی مبهم بود | در دیدبان جواب بدهید |
| سؤال باز | ریویو به چیزی رسیده که تسک تکلیفش را روشن نکرده | دیدبان با همین شروع می‌کند؛ جوابتان در حافظه‌ی پروژه ذخیره می‌شود |
| `Blocked` | ملکه نتوانسته جلو ببردش، یا دیپلوی یا چک زنده شکست خورده | دلیلش را در پنجره‌ی تسک بخوانید، بعد در دیدبان تصمیم بگیرید |

تأیید شما فقط برای یک کامیت است. اگر کامیت تازه‌ای بیاید، ریویو و تأیید شما از نو شروع می‌شوند.

## ۱۱. کار روزمره

- **کار فوری:** به دیدبان بگویید «این بعدی است». `High` را تنظیم می‌کند و ملکه آن را قبل از هر تسک منتظر دیگری در آن پروژه شروع می‌کند.
- **ایده‌ای برای بعد:** به دیدبان بگویید کنارش بگذارد. به `Technical debt` می‌رود که هیچ ایجنتی آن را نمی‌خواند، و در مرغزار علف هرز می‌شود تا این ستون کوچک بماند.
- **توقف یک پروژه:** کلید روی قطعه‌ی آن پروژه در مرغزار، یا در دیدبان بگویید «این پروژه را یک هفته متوقف کن». تا ادامه‌اش ندهید، هیچ چیزی به آن دست نمی‌زند.
- **توقف همه‌چیز:** **توقف** در داشبورد. قدمی که در حال اجراست تمام می‌شود و بعد از آن چیزی شروع نمی‌شود. **ادامه** کار را از سر می‌گیرد.
- **تغییر سقف‌ها:** **تغییر** کنار نوارهای مصرف. دور بعد با مقدارهای تازه کار می‌کند.
- **تغییر هر چیز دیگر:** `/kandu-config`، با گفتگو.
- **خودتان پشت فرمان:** روی هر تسک **باز کردن پرواز آزاد** را بزنید. یک سشن `Claude Code` با دسترسی کامل روی مغز باز می‌شود که می‌داند `worktree` و لاگ‌های تسک کجا هستند. کندو کنارش به کار ادامه می‌دهد.

## ۱۲. روشن کردن مرج خودکار

مرج خودکار خاموش شروع می‌شود. وقتی دیدید کندو همان تصمیمی را می‌گیرد که شما می‌گرفتید، یعنی همان نظرهای ریویو را می‌دادید و بدون ویرایش مرج می‌کردید، آن را برای هر پروژه با `/kandu-config` روشن کنید. حتی با مرج خودکار روشن، تغییر سخت‌برگشت همیشه منتظر شما می‌ماند.

## ۱۳. به‌روزرسانی کندو

<div dir="ltr">

```
git fetch upstream && git merge upstream/main
git push origin main
```

</div>

به‌روزرسانی هیچ‌وقت به `local/` دست نمی‌زند. بعد از به‌روزرسانی‌ای که سرویس‌ها را عوض می‌کند، در داشبورد **ری‌استارت کندو** را بزنید.

## ۱۴. وقتی چیزی درست کار نمی‌کند
