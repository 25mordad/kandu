# Kandu — design

Status: **early development; the main loop is built, but has not run on a real project yet.** This file is the full specification. The overview is in [README.md](README.md), the build roadmap in [TASKS.md](TASKS.md).

Everything that belongs to one person's setup (machines, paths, accounts, projects, limits) lives in config files under `local/`, which is gitignored. Examples: [config.example/](config.example/).

## 1. Setup and configuration — by conversation

Everything is configured by talking to an LLM in a Claude Code session. The one form is the quick way to add a project or a machine (§1B), and it follows the same rule: code reads the system first and the user confirms. The LLM **first inspects the system itself** and only asks what it cannot find out. For example, given a project path it reads the git remote, looks for existing boards, finds the test command in the project's files and works out how the project deploys, then asks the user to confirm. The result is plain YAML files in `local/` that can also be edited by hand. Each step ends with a real check that everything works.

### A. Initial setup — once per install (`/kandu-setup`)
1. Where does Kandu's brain (the supervisor) run: this machine or another one? Is that machine always on?
2. Which other machines are on the network, how are they reached (SSH alias), and which of them are always on? Should any give each run its own temporary folder on its own disk (`run_tmp`, off by default, §9)?
3. Claude access: subscription or API key? Usage limits: 5-hour window %, weekly %.
4. GitHub account, and the owners (users / orgs) Kandu may work in.
5. Where notifications go (Telegram or nowhere), which language Kandu talks to you in (`language`, default English), and which language its notifications use (`notify.language`, default `language`).
6. Defaults: number of parallel workers, wake interval, auto-merge on or off.
7. Prerequisites: `claude`, `gh`, `git`, `python` installed and logged in; `gh` needs the `project` scope for boards. Kandu says what is missing.
8. Didban (§13): which other sources may it read, and on which machine? On the machine you sit at, how is the brain reached?
9. Which port does the dashboard use (default 8790)?
10. Which model does each role use? A role not named runs on Claude's default. A project may name its own for any role but the queen's (§4).
11. May every role do everything, or should some be limited (`permissions`)? A role not named may do everything.
12. Should Kandu back itself up once a day (`backup`, off by default)? If so, at what hour, into which folder, and how many copies to keep (§12).
13. May the queen ask you to drop a blocker a task does not need (`supervisor.queen_drop_blockers`, off by default)? She only asks; the blocker leaves the issue on your yes (§5).
14. Should the dashboard list the open requests with their decision maps (`dashboard.show_requests`, off by default)? It only reads (§7).
15. Should a merged task's folders and `kandu/` branches be removed after its merge (`supervisor.clean_merged`, on by default)? A folder with work that is not in the PR stays (§4).
16. Which look does a browser open the dashboard in until it chooses its own (`dashboard.look`): Classic, the default, Classic new or Kandu Clean (§7)?

17. Should a task's `Reference` into another registered project's repo reach its runs as a read-only copy (`supervisor.reference_copy`, off by default)? Only the named paths are copied, and never from a private repo into a run on a public one (§9).

The dashboard itself is always Kandu's own (§7); only its port and its default look are choices.

### B. Adding a project — each time (`/kandu-add`)
1. Name, one line on what it is, which family it belongs to.
2. Which repos, and who owns them.
3. Where exactly it is: which machine, which path.
4. Permission to run: may Kandu clone it into its own work folder and run it there (`clone`), or must it work on that machine, in a separate `git worktree` (`in-place`)? **Always asked, never inferred.**
5. Does it have a board? Which one, and how do its columns map to Kandu's standard columns? If none, should one be created?
6. How is it tested and run locally, and, if `kandu.yaml` limits the workers, which extra tools do they need here (`allowed_tools`)? (The LLM proposes, the user confirms.)
7. How is it deployed: `direct` or `preview`? Which live URL is used for the final check?
8. Which secrets does it need and where are they? Kandu only stores the location, never copies or logs secret values.
9. Forbidden areas: e.g. migrations, payments, files that must never be touched.
10. Existing repo rules: CI, PR bots, other people working on the repo. Kandu respects them.
11. Merge in this project: automatic or with approval?
12. A daily token limit, and any rules for how the queen paces this project.
13. Priority relative to the other projects.
14. Project terms: the LLM proposes a short glossary from what it read, the user corrects it (§14).
15. Does the project keep its own reports for Kandu, such as a lessons file in its repo? They go under `reports`, read-only (§14).
16. The project's brief for Didban: the LLM drafts it from what it read, the user corrects it (§13, §14).
17. The daily Bazras, for a live project only: its hour and what it looks at (§5).
18. Who accepts a split proposal: the user (the default) or the queen (`split_approval`, §2).
19. Whether the queen's yes answers one-way merges: off unless the user says yes (`queen_answers_one_way`, §5).
20. Whether Kandu holds the project while its `main` is red: off unless the user says yes (`watch_main`, §5).

**The quick way:** the dashboard's settings tab has **+ Add a project**, and `python -m kandu.add` does the same from a shell ([kandu/add.py](kandu/add.py)). The user names the machine and the path on it, and the repo if git cannot tell. Code reads the rest from the copy there, changing nothing: the repo from its remote, the test command, a deploy script, the secrets file's location (never its values), the token names in `.env.example`, folders such as `data/` as forbidden areas, `AGENTS.md` and `CLAUDE.md` as repo rules, and a one-line description. It shows this as a proposal with warnings where it could not tell, and the user changes what they want and chooses where Kandu works on it (`clone` or `in-place`), which is never proposed. Nothing is written before the user adds it: the entry is validated on a copy of the config first, so a mistake leaves nothing behind; then a missing copy is cloned, a family with no board gets a new one, the entry is appended to `projects.yaml` so its comments stay, and the doctor's checks for the project are shown. Merging by itself starts off. A copy with no working tests gets a test that only compiles the code until `scripts/checks.sh` exists, and one with no deploy script gets a deploy that runs `deploy/deploy.sh` once it exists; for each the user may put a first task on the board that writes that script. A new machine is added the same way, from its SSH alias, and the dashboard says whether it answered. Each addition is logged (`project_added`, `machine_added`). The details the form does not ask, such as the brief, the glossary and Bazras, stay with `/kandu-add`.

**Removing a project** is one step too: **Remove from Kandu** at the bottom of its settings pop-up in the settings tab, acting on a second click, or `python -m kandu.remove NAME`, which Didban runs after the user's yes ([kandu/remove.py](kandu/remove.py)). What Kandu learned about it, its memory and its brief (§14), is first offered as a PR adding `docs/kandu-memory.md` to its own repo, made through the GitHub API so no copy is touched, for its owner to merge; a public repo gets no PR, since the memory may hold private details. If that PR cannot be made, nothing is removed until the user decides to go on without it. Then the project is paused so nothing new starts, its task sessions are closed, each of its workers is told to stop, and Kandu's worktrees beside its copies are removed, nothing else there. Only then is its entry cut out of `projects.yaml`, keeping every other entry and comment, after the new text passes the config's check on a copy; its memory and brief move to `archive/` beside them, never deleted. Work that cannot be stopped, a machine out of reach or a config that needs the entry fails with a clear message and leaves the config, and whether the project is paused, as they were. Its copy, repo, board and issues stay. Adding the project back brings its memory and brief back, with anything written meanwhile after them. The removal is logged (`project_removed`).

**Renaming a project** is a field in its settings pop-up: the name stands above its settings, and a changed name is applied only on Save, last, after the other changed settings ([kandu/rename.py](kandu/rename.py)). The new name is lowercase letters, digits and dashes, not starting with a dash, and no other project's; an empty or wrong one is refused with a plain message, and so is any rename while a supervisor cycle runs, or a worker or a free flight runs on the project ("stop or wait for the running work first"; the rename holds the cycle's lock, `state/supervisor.lock`, so no cycle starts during it), or while Kandu still keeps a memory, brief or Bazras report under the new name. The rename is one step that is complete or fully undone: its entry in `projects.yaml` (and `upstream.project` in `kandu.yaml`, when it names the project) takes the new name, line by line, after the config passes its check on a copy; its memory, brief (with its title) and Bazras reports move to the new name, and so do its pause, the settings the dashboard chose and its open requests. The event log is never edited: the rename is kept in `state/renames.json`, and every event written before it is read under the new name, so the Days tab and the daily token limit show one project with its full history. A project later given the old name starts with none of it. Anything that fails puts back every step already done, and the project keeps its old name. Each rename is logged with the old and the new name (`project_renamed`); renaming back restores it the same way. Its copy, repo, board and issues stay as they are.

After the questions, `/kandu-add` names a backup of what the project cannot rebuild as its first task, and offers a second one: the **repo note**. `python -m kandu.note NAME` renders it from the registry and only prints it. It is one generic template, [prompts/templates/kandu-note.md](prompts/templates/kandu-note.md), with no personal data: it says that Kandu's workers change the repo through PRs on `kandu/` branches, the merge mode, where the tasks are (the board, or Didban when there is none), the forbidden areas, and that a breakage goes back to Kandu as a task on the board, or through Didban, instead of being patched around it. It lives in `KANDU.md` at the repo root, and the repo's `CLAUDE.md` and `AGENTS.md` point to it with one line. The note reaches the repo only as a task for that project, filed on the user's yes; Kandu never writes it into a repo by itself, and adding it to a project already registered is that project's own task.

### C. Other conversational commands
- `/kandu-task` — define a task; writes the issue with the standard template onto the right board (§2).
- `/kandu-config` — change config: "pause project X for a week", "set the weekly limit to 50%", "remove this project".
- `/kandu-doctor` — health check in code (`python -m kandu.doctor`, no tokens): access, machines, `gh`, `claude`, the private guard, each project's copy, test tool and board columns.

The rules shared by these commands are in [docs/COMMANDS.md](docs/COMMANDS.md). What must hold for a task is enforced in `kandu/tasks.py`: the template's sections, and no private word in a public repo.

## 2. Task intake
- The user describes a task in a Claude session (`/kandu-task`). Claude writes it as a GitHub **issue** with a fixed template ([prompts/templates/issue.md](prompts/templates/issue.md)):
  - Goal
  - Current behavior
  - Acceptance criteria
  - How to test
  - Out of scope
  - `Blocked by` (if any)
- **Tokens:** a project names in `task_tokens` the tokens its tasks may use and what each is for. A task labelled `uses-tokens` is one that must really call a service: only its worker gets those values, in its environment, read from `secrets_from`, and being given the task is the user's yes for what it asks. Every other task gets none, so its tests mock the service. No agent can read the secrets file.
- Claude adds the issue to the right board with status `Backlog` and label `agent`. Only `agent`-labelled issues enter the loop. A task that is a breaking change also gets the **breaking mark**, the `breaking` label (§12).
- Each task gets its fields while it is refined: `Priority` (`High`, `Medium`, `Low`), `Kind` (`Bug`, `Feature`, `Chore`), `Size` (`Small`, `Medium`, `Large`) and, if it must be done by a date, `Deadline`. `kandu.tasks` refuses a task without them. The queen paces work from these fields, so organizing them is the job of whoever defines the task, not hers.
- A `Large` task must be split before it runs. It is split while it is defined, and `kandu.tasks` refuses to put one on the board; one the splitter later measures as `Large` waits for the user, or for the queen on a project whose split approval is hers. The queen may not release one, nor split one other than by accepting the splitter's proposal.
- **Size is measured, not declared.** The scale is in `kandu.sizing`: `Small` is up to 6 acceptance criteria and 18 changed files, `Medium` up to 10 and 36, and anything more is `Large`. So is a task that mixes work that is easy to undo with work that is not, since one such change would hold the whole PR at a one-way door.
- **`High` goes next.** On the user's word Didban runs `python -m kandu.priority`, which sets `High` and wakes the queen at the next look: the next cycle, or the end of the task in hand. While a `High` task can start, code refuses any other release in that project and it runs before any other waiting task. Nothing running gives way, and a task it is blocked by comes first.
- **Technical debt.** A task the user chooses not to refine yet is parked in the `Technical debt` column with `python -m kandu.debt add`: an English title and a short text, no fields. No agent reads this column, so the splitter never sizes it and the queen never sees it. Didban opens by saying what is parked, and `python -m kandu.debt promote` moves a task to `Backlog` only after the user's yes, with the checks of any new task. The dashboard counts these tasks and the meadow grows them as weeds, so the column stays small.
- **Done.** A finished task leaves the field and fills a cell of the comb under the meadow for 5 days after its issue closes, so the recent work stays in sight. A cell opens what the task was and what it cost. The dashboard reads this from the board, and it changes nothing there.
- **Bazras** (Persian for "inspector") is a separate bee that looks at a live project's health once a day and changes nothing. It is off for every project until the user turns it on (`inspect.enabled`), in the dashboard's Bazras tab or in the registry. Only such a project gets one look a day, at its own hour (`inspect.at`, default `bazras.at`); `kandu-bazras.timer` wakes every 15 minutes and looks at each project whose hour has come and has no report today. Code does the looking, with no model: the last 24 hours of commits on the project's base branch (§5) (which carry `Kandu-Run:`, which Kandu commits were reverted, which other commits changed again files a Kandu commit changed in the last week, minus `ignore`), the state and logged errors of the listed systemd units and timers, the error lines added to the listed log files since the last look, the listed crontab lines, the test command and the project's own check commands in a fresh checkout. A non-zero exit or a failed unit is a finding. Only when there are findings does one read-only run judge them: what broke, its likely cause, and a draft task when one is worth it. Its tools are fixed in code to reading and `git log`, `show`, `diff` and `blame`, whatever `permissions` says; it cannot edit, push, call `gh` or read the secrets file. The judgment counts against the project's daily limit and is skipped past it, past the usage limits and with the stop file; the report then says the findings were not judged. The report is short, dated and private, in `local/reports/bazras/<project>/`, and code hides emails, secrets and tokens in it. For each log with errors it shows the most common kinds of error with their counts, each line reduced by code to its kind, with numbers, ids, times and quoted values taken out. With nothing found it is the one line "All was well." Bazras creates no task and changes no board: Didban brings the findings up and the user decides (§13).
- **The splitter** is a separate bee. Every task in `Backlog` gets one read-only run before the queen can see it. These runs only read, so all unsized tasks are sized in the same cycle, up to `supervisor.max_parallel_sizers` (default 4) at once; and its report is checked in code against the scale. It reports the files the task touches and its door, and code refuses a size smaller than those facts. Its answer goes in the `Size` field and a `task_sized` event; the local log is what the queen's lock reads, since a worker could edit a board field. A run that fails sends the task to `Needs info`, and moving it back to `Backlog` sizes it again.
- **A task that needs a forbidden area is held.** The splitter also lists which of the project's forbidden areas the task must change to be done, always as a list and empty when none; code refuses a report that names an area the project does not forbid, as any other bad report. A task that needs one stays in `Backlog`: a `task_held` event records the areas and the splitter's reason, its issue gets a comment that names no area, nothing is split, and the queen neither sees it nor may release it. Didban opens with the held tasks and their areas (`python -m kandu.split held`). Once the user has opened the area or changed the issue, `python -m kandu.split release TASK` records `hold_released`, and the task is sized again as it then reads. A task that needs no area goes on exactly as before.
- **A large task waits for the user's yes.** The splitter proposes slices and the task moves to `Needs split`. Each project's **split approval** says who accepts its proposals: `user` (the default) or `queen`, set as `split_approval` in the registry or with «When a task is too big, the split is accepted by» in the project's settings pop-up; the switch's choice is kept in Kandu's state, wins over the registry, and each change is logged with the project, the old value and the new one (`project_setting_changed`). While it is the user, every proposal waits for the user's yes, also when every slice is `two-way`. While it is the queen, each proposal in `Needs split` reaches her look with its reason, its slices and each slice's size and door, named by its version (the fingerprint the dashboard's yes uses); a proposal she has not seen wakes her once, and one she left wakes her again only once it changes. She may accept it (`accept_split`, with the version she read and her reason) or leave it; she has no way to decline or change one. Code carries out her accept through the user's own yes, `split.approve`, with all of its checks, and refuses it on a project set to the user, on a proposal that changed since she read it and on a task no longer in `Needs split`. An accepted proposal makes the slices as the user's yes does, is logged as `queen_accepted_split` with the slices and her reason, and the user gets an information notification naming the task and its slices. A proposal she leaves stays in `Needs split` for the user, as on a project set to the user; `auto_merge` is untouched, so a project the user merges by hand still waits for the user's merge. A change reaches only later proposals: one already accepted and a split already made stay as they are. The proposal stays in local state, as an issue may be public. The dashboard shows each proposal with a button to accept it, and Didban opens by saying what waits there. Issues are created only on the user's yes, or the queen's where the project lets her. Declining or changing a proposal happens in Didban: on a no the task returns to `Backlog` and is sized again.
- **A group** is the slices of one task. Each is blocked by the one before it and has its own PR. The chain orders only the merges: slices are built and reviewed side by side, with each other and with the project's other tasks, and a slice's PR merges only after the one before it. The first slice inherits the task's blockers. The parent issue closes with the last slice. A task that names the split task under `Blocked by` waits for its last slice instead: since slices merge in order, the last one closing means all are done. When the split is made, code rewrites every open task that names it, before it records the split, so a retry after a failure part-way rewrites the rest and names no slice twice. A task defined later, by the user or the queen, that names a split task gets its last slice in its place, and the user is told: `kandu.tasks` prints it, and a task the queen opens is a notification. Each rewrite is logged with the task, the old blocker and the new one (`blocker_rewritten`). A slice split again leads on to its own last slice. Only the references change: the words and comments the author wrote under `Blocked by` stay. A task whose blockers were not split is left as it was. The merge gate reads a split blocker the same way, so a task that still names one, from any path, waits only for its last slice: the reason shown names that slice, and the wait ends when it closes, though the split task is still open.
- **After the fact.** A PR with more files than its size allows is logged as `oversized`, as a warning only, which shows where the scale or the estimates are wrong.
- On a public repo the issue is public too: no private details in the task text.
- **A spec** holds a request that becomes more than one task, so the whole request is still on record after its tasks merge. While defining (§13), its issue is written first, from [prompts/templates/spec.md](prompts/templates/spec.md): Problem, Solution, Decisions (from the decision map) and Out of scope, and it is created only on the user's yes. `kandu.tasks --spec-issue` refuses a spec that lacks one of the four sections, and checks its language and private words as a task's. A spec is never work: it gets no `agent` label, no fields and no card, so it is never sized and never reaches the queen; even put on a board by hand with the label, code keeps the splitter, the queen and the workers away from it. Each of its tasks is made with `--spec #N`: code refuses a reference that is not an open spec of the same project, writes `Spec: #N` at the top of the task and replaces the task's `Out of scope` with the spec's. The local log records the spec (`spec_created`) and each task that names it (`spec_named`), and the spec closes when the last of those tasks closes, however it ended (`spec_closed`); a spec no task names yet stays open. The spec's Solution, Decisions and `Reference` sections reach the prompts of the task's worker, reviewer, second review and splitter, under `## The task's spec`, read from Kandu's copy of GitHub with no GitHub call. The worker is told the decisions are part of its assignment and a change that contradicts one is out of bounds; the reviewers are told such a change is a blocker that names the decision. A task with no spec, or whose spec the copy does not hold (or that has none of those sections), gets the prompts it got before, and the run records `spec_unreadable` when a named spec could not be read. Nothing is copied into the project's repo.
- A precise task (clear acceptance criteria) and real tests in the project matter more for the result than the loop itself. That is why defining tasks is a conversation, not a form.

What makes a task good:
- **English.** Everything on GitHub is in English, whatever language the user speaks, so no agent writes or reads a translation: titles, bodies, sub-tasks, PRs, comments and reviews. The user's language is for the dashboard's own text and for what the queen tells them. `kandu.tasks` refuses a task in any other language.
- **Not in `.claude/`.** Claude Code refuses edits there in an unattended run, whatever the allow list says; a worker can only delete those files. A task that must edit them needs that edit made by hand first.
- **Behavior, not steps.** It says what the software must do, not how to change it. No file paths or line numbers: they go stale before the worker starts. The one exception is the `Reference` section of the issue and the spec: when the user asks to copy or match existing work, it names the repo, the paths and what is to be copied or matched (look, steps, behaviour). `kandu.tasks` does not require the section, since most tasks copy nothing. Each task that touches the source carries its own `Reference`, never only the spec, with an acceptance criterion that checks the result against it. Defining checks that each reference can be read from the machine the project's worker runs on and, when it cannot, says so and names a read-only copy that lives only in the run's folder, never in the project's repo.
- **Each acceptance criterion can be checked on its own**, and "Out of scope" stops the worker from growing the task.
- **One slice.** A task is sized to one fresh context and delivers a complete path that can be verified alone, not one layer of a feature. Refactoring that makes the work easier comes first, as its own task.
- **A wide mechanical change** (a rename across the whole codebase) is the exception: add the new form beside the old, move callers over in batches, then delete the old form. Each is a task, and each leaves the tests green.
- **The order is explicit.** `Blocked by` names real issues, so the supervisor can always see which tasks are ready. It names only a task this one cannot work or merge correctly without, never a related one, since each name holds the merge; Didban's instructions, `/kandu-task` and the issue template all say so. A blocker holds back only the merge: a task may be built and reviewed while its blockers are still open, and its PR merges once they are all done. A worker whose blocker is still open is told so, builds on the base branch and reports `blocked` if it cannot do the task without that blocker's code. A blocker may also be set as a GitHub "blocked by" relationship, in GitHub's interface or by another tool: a task's blockers are the references under `Blocked by` joined with its relationships, as the copy keeps them (§3), and one named in both places counts once (repo names compared without case). The merge gate, the worker's note, what the queen sees and the dashboard, on the task and on its PR, all read this one set, and a relationship blocker that was split waits for its last slice as one in the section does. Dropping a blocker takes it out of `Blocked by` and out of its relationship, wherever it is held (§5); writing one to the issue touches only `Blocked by`.

Before writing the issue, `/kandu-task` and Didban check that the behavior does not already exist and that it was not rejected earlier (§14). Both follow one file, [prompts/defining.md](prompts/defining.md), so workers can change it; the command only points there. Every task starts from the code it touches, so its scope is known before a worker sees it. How it will be done is shown to the user and stays out of the issue. Before the final text, a coverage list pairs each ✅ line of the decision map with the task and the criterion or `Out of scope` line that holds it, and nothing is created while a line has none.

Then it interviews the user in rounds until no decision is open, written for a user who is not a software engineer: Kandu brings the questions an engineer would ask. Each round asks every question that can be decided now; one that depends on another's answer waits. Each question says in one line why it matters and gives a recommended answer, and "yes" accepts them all. It looks up itself what the code can answer, asks only about outcomes, and makes the technical choices itself, stating each as an assumption the user can reject. After each round it shows the **decision map**: ✅ decided, ❓ asked now, ⏳ waits, ✂️ out of scope. It ends only when the map holds no ❓ or ⏳ and the user has said yes to a summary of the shared understanding; a small task has fewer rounds but the same end. A confirmed decision that shapes later tasks goes into the project's brief.

**In two steps.** Beside `/kandu-task`, `/kandu-grill-with-docs` and `/kandu-to-issue`, adapted from Matt Pocock's skills (MIT), define a request in two steps, and work inside Didban too, where the first takes the place of the interview of [prompts/defining.md](prompts/defining.md) for that request; its other steps, checks included, stay as they are. The interview asks the whole frontier of a design tree at once, lets the user stop to clarify, and saves the whole tree as the request's decision map after each answer, so no decision lives only in the session. The interview's final summary also holds the testing seams and the planned tasks with their fields, so the user's yes to it is the yes to the spec and every task: `/kandu-to-issue` asks nothing, takes a stated default for a field left open and names it as an assumption in the spec. `/kandu-to-issue` always writes a spec, even for one task, since the spec is where the decisions are kept once the request closes: its Decisions hold every decided line of the map and a `Glossary` section holds the words the user settled. Each word and each decision marked as hard to reverse is written in the same PR as the change that first uses them: `/kandu-to-issue` gives that task an acceptance criterion naming each word for the project's `GLOSSARY.md` and each such decision for its `docs/adr/`, and no separate task records them. A repo with no `GLOSSARY.md` gets no word criterion, and no task creates the file. The worker adds a new project word it names to an existing `GLOSSARY.md` in the same PR, and the reviewer reports one left out as a note that does not block.

## 3. Boards
- **One GitHub Project board per project family**, owned by the GitHub user or org the repos live in. One family can hold many repos; the built-in `Repository` field tells the supervisor which repo an issue is in.
- Standard columns on every board, so the supervisor handles them all the same way: `Backlog`, `Technical debt`, `Ready`, `In progress`, `In review`, `Needs info`, `Needs split`, `Blocked`, `Done`. `python -m kandu.boards --add-missing` adds a new column to an existing board, keeping its items in place. An existing board with other columns is mapped onto these during `/kandu-add`, under `board.columns`.
- `Backlog` holds approved tasks. `Ready` means work may start: the queen moves tasks there at the pace of each project, and a task the user moves there by hand starts as well.
- Each board also has the fields `Priority`, `Kind`, `Size` and `Deadline`. `Type` is a name GitHub keeps for itself, hence `Kind`.
- **Kandu works on its own copy of GitHub** (`kandu/mirror.py`, in `state/mirror/`), so GitHub's limits and outages do not stop tasks. Every Kandu process reads boards, issues, PRs and default branches from the copy, never from GitHub directly; only what the copy lacks, such as an old issue named as a blocker, is read once and kept.
  - **Reading:** one request a repo reads what changed in its issues, with their comments (a new comment changes an issue's `updatedAt`), every open PR whole (checks and review threads change without touching a PR's `updatedAt`) and the PRs closed lately; one request a board reads its cards. The copy is read again every `github.sync_every_minutes` (default 10) by `kandu.sync`, when the supervisor wakes, and on every order from the user: a Didban command or the dashboard's board-read button. After an agent pushed or opened a PR, the supervisor reads that repo or PR at once.
  - **Writing:** a change goes into the copy at once and waits in a queue (`outbox.json`). `kandu.sync` reads first, then sends the queue: card changes in one request a board, the rest one by one with a pause between. A refusal that passes by itself (a 5xx, a limit, the network) keeps the change for the next send; any other refusal drops it to `dropped.jsonl`. `python -m kandu.sync --queue` shows both.
  - **What the copy keeps:** each issue with its title, body, state, labels, last 100 comments and the issues GitHub's own "blocked by" relationships say block it (repo and number, the first 50), on the issue and on its card alike, since every board read gives each kept issue its card's list, which a repo read by `updatedAt` could miss; an issue or card kept before the copy held them reads as blocked by none. A task's blockers are these relationships joined with the references under `Blocked by` (§2); each PR with its comments, and an open one with its files, checks and review threads, each thread with its file, line, whether it is resolved and its first 20 comments. A queued comment shows in the copy at once, and so does a removed "blocked by" relationship, which is sent as `DELETE .../dependencies/blocked_by/{issue id}` and leaves the queue quietly once GitHub no longer holds it.
  - **One item from the copy:** `python -m kandu.show OWNER/REPO#NUMBER` (or the issue's or PR's URL) prints an issue with its comments, or a PR with its checks, review threads and comments, and changes nothing. The text keeps its shape: a head of `key: value` lines (`issue OWNER/REPO#N: title` or `pr ...`, then `state`, for a PR `draft`, `mergeable`, `branch: NAME @ SHA` and `files changed`, then `labels` and `url`), the body, then each list under its count (`checks: N`, `review threads: N`, `comments: N`), a comment as `--- author, time` over its text. `--json` prints the item as the copy holds it, with `kind` and `repo`. What the copy holds costs GitHub nothing; an item it does not hold yet (an issue older than the copy, a PR long closed, an issue kept before issues kept their comments) is read once and kept, so the next call reads nothing. A repo with no copy yet is read whole first, as for any read. It exits 1 when GitHub has no such issue or PR or refuses the read.
  - **How agents read a task:** a worker, splitter, reviewer, second review, check, live check and the queen read the issue and the PR with `<kandu>/bin/kandu-show OWNER/REPO#NUMBER`, which runs `kandu.show` from any folder; each prompt names the command with the item filled in. A reviewer, second review and check read the diff from their own checkout with `git diff origin/BASE...HEAD_SHA`, the base being the project's base branch (§5). No instruction Kandu writes names `gh issue view`, `gh pr view` or `gh pr diff`, and a test holds it. A worker still comments with `gh`, as its permissions allow; Kandu opens its PR. The command lives on the brain, so it serves agents that run there. A project on another machine (its `machine` is not the brain's) cannot run it: Kandu reads the issue and the PR (and a reviewer's companion PRs) from its copy on the brain and puts each into the prompt under `## Kandu's copy of OWNER/REPO#N`, in the text `kandu.show` prints, and the fact line points there. A review or check there still reads the diff with `git diff` in its checkout. No agent there reads GitHub with gh either. The queen always runs on the brain and keeps `bin/kandu-show`.
  - **Reading by hand:** the dashboard's read button syncs both ways: it reads GitHub into the copy and then sends the queue, in the same order as `kandu.sync`, so every local change shows on GitHub at once.
  - **Writes that go at once:** a merge, because the next step needs GitHub's answer, and creating an issue, whose number names the task (through the REST API, which has its own limit). Opening a PR and replacing its description: a worker's last message brings the title and the description, and Kandu sends them as arguments of `gh api`, from the task's own branch into the default one, always with `Closes #N`. A PR an earlier run left open on the branch gets the new description instead, and an open call whose answer was lost is checked against GitHub before it counts as a failure. After a fix round or the queen's rework a new description replaces the old one; a refused edit is recorded (`pr_body_not_edited`), and the round is still judged by its commits.
  - **The newer change wins.** A queued card change stays in the queue until GitHub holds it. If the field changed on GitHub meanwhile, the board read compares times: a move made on GitHub after the change was queued (by the field's `updatedAt`) stands, and the queued change is dropped and logged in `dropped.jsonl`; an older move is overwritten by the next send. A value Kandu itself sent is never taken for someone else's move, so a clock a little apart drops none of Kandu's own changes. A move made on GitHub stands when nothing for that field waits in the queue.
- Kandu creates a board only when the user says so.
- **A board several people share** (`multi_user`, a project setting, off by default): each person runs a Kandu of their own on the same board, and a task belongs to whoever it is assigned to on GitHub. While it is on, an install sees only the cards assigned to its own account (`github.account`, compared without case): every reading of the board, in the copy and from GitHub, leaves out the rest, so the splitter, the queen, the workers, the by-hand labels, the technical debt and the dashboard never reach another person's task or an unassigned one. A person assigns a task to themselves first and their Kandu then picks it up. Every issue an install makes on such a board (a task, a slice, a parked note) is assigned to its account, so it stays in its sight. While it is off, who a task is assigned to does not matter and the install works every task, as before. The projects of one family share a board, so they are all multi-user or none; `board.assignee` is set by Kandu from the setting, never by hand. It is set in the registry or with «Shared by several people» in the project's settings pop-up, which writes the registry.
- A task only a person can do stays on the board without the `agent` label, so it is visible and Kandu leaves it alone. On GitHub it carries the `by-hand` label instead, given when `kandu.tasks --by-hand` creates it, in the copy at once; a spec gets neither label. The first `kandu.sync` that reads every board and repo gives it, by itself and once, to the open by-hand tasks made before the label, and a marker in the state keeps later syncs from doing it again; `kandu.tasks --label-by-hand` does the same by hand. A task with `agent`, a spec, a task done or closed, and one labelled already are left alone, so a second run asks GitHub for no change. Kandu still tells a by-hand task by the missing `agent` label, not by this one. The dashboard shows it too, marked by hand, with the free-flight button, so the user can work it in a session. The workers never see it, and the queen sees it only to name it: each project's open by-hand tasks reach her look by number and title, so her brief names them and never calls a Backlog that holds one empty, while code refuses any decision of hers on one, as on a task of no running project, and the splitter never sizes it. While it is in an open column, not `Done` and not closed, it also carries the orange «waits for you» mark and counts in the dashboard's count of what waits for the user. It then reads as the user's own work: its flower draws a hand in place of the queen's crown, shown in the legend too, and never the «unsized» mark; the task list and its dialog name its state «By hand, waits for you», never «Waiting for the queen». Its dialog carries the «waits for you» chip, says that no agent works it and the queen never picks it, that the user does it alone or with the free flight in the same dialog, and that closing its issue moves it to `Done`, and shows its issue's goal and acceptance criteria, read-only, from the copy.

## 4. Project registry
One entry per project in `local/projects.yaml`, written by `/kandu-add`. **A project not in the registry is never touched.** Fields (see [config.example/projects.example.yaml](config.example/projects.example.yaml)):
- repos and board
- `base_branch`, optional: the project's **base branch**, the branch of its repos that Kandu works on and merges into, such as `dev` when `main` is production. Without it, it is each repo's default branch on GitHub, so a project that names none works as before. See "Base branch" in §5. `/kandu-add` asks for it, proposing the repo's default branch, and `/kandu-config` changes it; the dashboard's settings pop-up shows it, read-only, in every look.
- **run location**, set by the user per project, never inferred:
  - `clone` — Kandu may clone it into its own work folder on the brain's machine and run it there;
  - `in-place` — must run on a named machine, in a separate `git worktree`, never in the user's own working copy.
- machine, path, test command, local run command, extra `allowed_tools` for its workers (used only when `permissions` limits the worker)
- `setup`, optional: a `command` a fresh checkout needs before its tests can run, such as `npm ci`, and the `inputs` whose change needs it again, such as `package-lock.json`. Kandu runs it itself before every run of the project's `test` in a checkout of its own: the merge gate, the end-of-cycle check and Bazras. It runs in a checkout that never had it, and again when one of its `inputs` changed since, or, with no `inputs`, when the head did. A mark in the checkout's own git folder (`kandu-setup`) says what the last setup was for, so a setup cut off halfway or one that failed runs again and the project's files never show the mark. A setup that fails counts as failing tests, and its output is in the test's log. Workers and reviewers are told the command and may run it. `/kandu-add` proposes `npm ci` when the copy has a `package-lock.json`.
- a project with several repos keeps each at `<path>/<repo name>`
- `models`, optional: the model each of its roles runs on, for `worker`, `reviewer`, `splitter`, `live_check` and `bazras`. A role it does not name runs on `claude.models` in `kandu.yaml`, and without one there on Claude's default, so a project with no entry runs as before. The queen works for every project at once, so her model is set in `claude.models` only. The config check refuses any other role and a value that is not a model name, naming the project and the role. The settings pop-up changes it (§7); the next run uses it, and a run already at work finishes on its model
- `deploy`: `mode` (`direct` or `preview`), `command`, `live_url` (leave it out when the live software is behind a login: the task is then done after the deploy, with no live check)
- where its secrets are, the `task_tokens` its tasks may use with what each is for, forbidden areas, repo rules, merge mode, priority, max parallel workers, daily token limit, the queen's rules for this project, who accepts its split proposals (`split_approval`), whether the queen's yes answers its one-way merges (`queen_answers_one_way`), whether a red `main` holds it (`watch_main`, §5), whether several people share its board (`multi_user`, §3), paused

**Machines that are not always on** (e.g. a laptop): at the start of each cycle the supervisor checks the machine over SSH. Reachable → run the worker there. Not reachable → skip that project's tasks; they show as "waiting for machine" and are picked up the next cycle it is reachable. Leaving the machine on is enough to let Kandu work on it.

**Worktrees** sit beside the copy, in `<path>.kandu-worktrees/`, never inside it, so they never show in the user's `git status`. A worker's worktree is kept between runs, so a cut-off run leaves its work for the next one. A merge, rebase or cherry-pick an earlier run left unfinished there is cancelled before the folder is used again, and recorded (`worktree_cleaned`). When git refuses to cancel it, as when a file was changed again after it was staged, the operation is dropped and the folder reset to the task's branch, losing only changes that were never committed; if the folder also holds commits that are not on GitHub, it is left as it is and the task stops in `Blocked`, saying so. A reused worktree is then brought to the branch on GitHub: one behind it is fast-forwarded, one equal to it or ahead of it keeps its own commits, for the worker to push. One whose branch has drifted from GitHub's, each with commits the other lacks, is settled so that no commit of either side is lost, and how is recorded (`worktree_settled`): when every commit only on GitHub has a copy with the same change in the folder (a merge commit never counts as copied), as when a run rebased the pushed work onto a newer base and added to it, the folder's branch is pushed over GitHub's with `--force-with-lease` on the head Kandu saw; otherwise GitHub's head is merged into the folder's branch, for the worker to push. If that merge conflicts, uncommitted changes stand in its way, or GitHub's branch moved so the lease is refused, the folder is left as it was and the task stops in `Blocked`, saying why Kandu cannot settle the two branches safely. A reviewer gets a separate checkout of exactly the head `SHA`.

**Cleanup after a merge:** once a task's PR is merged, by Kandu, by the user's yes or by hand on GitHub, the end of the next cycle removes what Kandu made for it: its worktree, every review checkout of it (`<slug>-review`, `check-<N>-review`), its local `kandu/` branch and that branch on GitHub. It is code, on the project's machine through the runner (§9), and costs no tokens. Only folders under `<path>.kandu-worktrees/` that are worktrees of the copy, and only a task's own `kandu/<N>-<slug>` branch, are ever touched; the copy itself, deploy checkouts and every other branch never are. A folder stays when it holds uncommitted changes (files git ignores do not count) or commits found neither in the merged PR nor on GitHub; a local branch stays when such a folder holds it or it has such commits; the branch on GitHub stays when it was pushed to after the merge. Each stays alone: the task's other folders and branches still go. Each removal is logged (`cleaned`), and each folder or branch that stays (`clean_kept`) shows on the task's page with its reason. A PR closed without merge leaves everything. While a free flight on the task is open everything stays, and the first cycle after it closes cleans up. A flight opened before the merge ends by itself, as part of this cleanup and under its switch, at the first cycle after the merge in which nothing was written in its session for 120 minutes (its transcript's last change, or its start); it is summed up as any ended flight, the end is logged with the task and the reason (`flight_ended`), and no notification is sent. A flight opened after the merge is the user's to end. A machine that cannot be reached waits for the next cycle and holds no other machine back. Only PRs merged after the first cycle that had this (`state/clean-since`) are cleaned; older leftovers stay. Once done (`clean_finished`), a task is not looked at again. It is on by default (`supervisor.clean_merged: true`), an exception to new features shipping off that the user chose, and one switch in the dashboard's settings turns it off.

## 5. Supervisor, workers, reviewer

```
queen (LLM, one for all projects: wakes at the start, and when a task ends)
  │ releases tasks, judges what stopped
supervisor ─┬─ worker 1  →  reviewer
            ├─ worker 2  →  reviewer
            └─ ...
                 ↓
   supervisor: final check → merge → deploy → check in the live software
```

- **Supervisor:** a code loop on the always-on machine ([kandu/supervisor.py](kandu/supervisor.py)), not an LLM session. Everything that needs no judgment runs there, at no token cost, and still works when Claude is down: gates, task selection, starting agents, review rounds, the `SHA` check. It **writes no code**. A headless `claude -p` session is started only where judgment is needed, such as the final check (task 12). It never grades its own work.
- **Queen:** the LLM that runs the cycle for every project ([kandu/queen.py](kandu/queen.py), [prompts/queen.md](prompts/queen.md)). There is one queen, and each look covers all projects. She is a fresh `claude` process on the brain's machine, told to change nothing, not one long session, so the cost of a waiting queen is nothing.
  - **When:** at the start of a cycle, and each time a task ends, if code finds something to decide: a new or changed `Backlog`, a stopped task, a failed project check or a new reason for a merge to wait. She sees an unchanged `Backlog` once a day. An open by-hand task she has not seen wakes her once, so her brief can name it; the same set of by-hand tasks never wakes her again (her look records it as `by_hand`). A quiet cycle costs no tokens. `supervisor.queen: false` turns her off, and only `Ready` tasks then run.
  - **What she sees:** each project's fields, `queen_rules`, tokens used and limit, and the events since her last look. She reads no task body until a task is a candidate, so a long `Backlog` stays cheap.
  - **At work:** her `at_work` counts a project's tasks a worker builds or is about to: those in `Ready` and `In progress`. A task in `In review` takes no worker's place, as in the supervisor, and neither does a task whose merge is held only by its blockers on the head it was held on; a new head, a dropped blocker, a new merge decision or a worker's step on it counts it again, while her own decisions and asks on it leave it held. A held task is listed under `waiting` with the blocker it waits for, so on a one-worker project it never keeps her from releasing that blocker.
  - **What she decides:** she sees a stopped task through as the user would, and asks the user only when nothing else can move it. `release` moves a task from `Backlog` to `Ready`; `retry` sends a stopped task back to `Ready`, or to `Backlog` when sizing failed; both carry a note the next worker reads. `rework` sends a fresh worker to the task's open PR with her order, and the new head is reviewed as usual. On a PR that conflicts with its base, Kandu first merges the base in as an update round does, since a worker never runs `git merge` and an update round that already stopped on that head is not run again: a clean merge it pushes, and one with conflicts it leaves open, for the worker to resolve and to do her order in the same round. Conflict markers left in those files stop the task in `Blocked`, as after an update round. `verify` sends a checker, a read-only run with the reviewer's rules, to find one thing out on the PR's head or the project's base branch; she reads its answer at her next look. `new_task` opens a task in the same repo with every check of a new task, and may make the stopped task wait on it; `block_on` makes a merge wait for another task. Both write under the issue's `## Blocked by`. `approve` answers a merge's questions and its door for one head `SHA`, as the user's yes would, but never stands in for `auto_merge`; `ask_user` puts a question on the dashboard. `drop_blocker` is a drop ask: she asks the user to drop one named blocker the task does not need, with her reason. Code refuses a blocker the issue's `## Blocked by` does not name, and changes nothing on the issue: the question shows on the dashboard beside her others, with a yes button, until the user says yes, the blocker is gone, or the task ends. The yes takes out only that blocker, from `## Blocked by` when the issue names it there and from its GitHub "blocked by" relationship when it has one, so a blocker held in only one place drops too and does not come back; a question whose blocker is in neither place no longer shows. Both writes go through the queue (§3). It records `blocker_dropped`, and the next cycle checks the merge again. It ships off (`supervisor.queen_drop_blockers: false`), and the user turns it on in the dashboard. `accept_split` accepts a split proposal, as the user's yes would, only on a project whose split approval is hers (§2). She also sees what waits (`Blocked`, `Needs info`, a merge that waits) with its newest reason. Her brief goes to the dashboard. Her notes stay local, since an issue may be public.
  - **Loop guard:** each of `retry`, `rework`, `verify`, `new_task` and `block_on` may be taken `supervisor.queen_max_retries` times per task (default 3), and she is shown her steps so far. A step past its limit is not taken: code stops the task in `Blocked`, records `loop_stopped` and tells the user once. She takes no step on that task again until the user acts on it. With the queen on, a stopped task no longer notifies the user by itself, since she sees it first; a failed deploy or live check still does.
  - **Locks she cannot pass:** code carries out each decision on a fresh read of the board, and refuses one that breaks a rule. She cannot merge, deploy or edit, and her yes passes no other merge condition. She cannot release a task the splitter has not sized, a `Large` or closed task, one of a project at its limit, or anything but the `High` task that goes first. A task the user stopped, or one whose PR is merged, does not go back, and the loop guard caps her steps on each task. The usage limits, the stop button, the `SHA` check, `wait_for_user` and the denied paths stay in code.
  - **Daily limits:** each project has `daily_token_limit`, and she has `supervisor.queen_daily_token_limit`. Cache reads do not count. A project at its limit starts nothing new, even a task the user moved by hand; work already running ends normally, so a limit can be passed a little. At her own limit she sleeps and nothing new starts anywhere, since no one is planning.
  - **Cost:** each look is recorded as a run with role `queen`, and the dashboard shows that look, today's total and her limit.
- **Replies:** every agent ends on one JSON object, held to a JSON Schema by `claude` where the role has one, and code reads the object even when a summary or a code block wraps it. A reply code still cannot read is asked for once more in the same session, with "do not redo the work", so a finished task does not stop on its last message alone. A first run whose reply still cannot be read but whose branch is pushed gets its PR from Kandu, with the issue's title and a description that says so; the review reads the code.
- **Kandu's own trouble:** a run that crashed, a reply still unreadable after the second ask, a GitHub refusal that passes by itself (5xx, a rate limit, the network) or a machine that did not answer is not the task's fault. The task stays where it is, with no comment, and the next cycle tries it again. Only when it comes back three times in a row, with no review, sizing or end in between, does the task stop in `Blocked` for the queen. A `rework` or `verify` of hers that it stopped is ended then, as `queen_step_done` with the result `failed` and the error, so no later cycle takes it again; she reads that it failed, and why, at her next look. The task's card says which try failed and how many Kandu makes ([kandu/tries.py](kandu/tries.py)), and offers to stop the tries at once, as if the last one had failed, which starts a cycle so the queen looks now; it is refused while a try runs. A fix or update round that pushes nothing is recorded (`round_no_commit`, with the worker's reason), so the card can say why the task does not move.
- **Workers:** separate `claude` processes, started by the runner layer (§9) on the project's machine, each in its own `git worktree`, so they never write over each other. Separate processes are what let Kandu stream each worker (§7), stop one alone and record its tokens. Tasks run in parallel, up to `max_parallel_workers`, whether or not one blocks another; only their merges follow `Blocked by`. A task in review takes no worker's place, so every PR waiting for review is reviewed in the same cycle. Their instructions are in [prompts/worker.md](prompts/worker.md):
  - Tests come first, at the project's public interfaces, and they check behavior rather than internals.
  - A bug starts with one fast command that fails on exactly that bug. If no such command can be built, the task goes to `Needs info` instead of a guess.
  - Every PR uses [prompts/templates/pr.md](prompts/templates/pr.md): a small summary, before and after evidence, and the blast radius. A worker runs inside another project, so the runner puts this template in its prompt.
- **Live checker:** a fresh `claude` process ([prompts/live-check.md](prompts/live-check.md)) opens the live version after deploy and reports `pass` or `fail`. It changes nothing.
- **Reviewer:** every PR gets one review by a fresh `claude` process ([prompts/reviewer.md](prompts/reviewer.md)). "Fresh" means it knows nothing of how the PR was built; it does get the project's rules and memory. It reads the diff, searches the whole repo, runs the project's tests and whatever check, script or page a criterion rests on, and writes a report; it changes no code. A criterion it could show by running it is not left `not_shown` because the author did not run it.
  - **Blockers:** a bug that breaks production, a security hole, a crash or unhandled error, an unmet or unproven acceptance criterion, a change out of scope or in a forbidden area, and new logic with no test that really runs it. There is no coverage percentage.
  - **Notes:** smells and broken documented rules that are not blockers. Cosmetics, small design issues and product decisions are not reported at all.
  - **Verified:** each blocker is pressure-tested before it is reported: the head is checked again, the bug is separated from the stated reason, every caller in the repo is traced, and a path that really reaches the bug is found.
  - **Companion PRs:** an open PR in the same family is a companion if a PR body names it or its branch has the same slug. The reviewer checks that the two sides really work together, not only that the names match. Nothing else is assumed to be a companion.
  - **Report:** one JSON object, validated in code. It holds the reviewed `SHA`, each criterion's result, each finding with path, line and kind, what was checked and found sound, the door, a plain brief in English, and the same brief in the user's language for the dashboard, which stays in the local log. Nothing found is a valid result.
  - **Scope:** a first review answers the issue's acceptance criteria and reads the PR's own changes. Code takes the criteria's text and count from the issue, so a reviewer cannot add or reword one, and drops a finding that neither names an unmet criterion nor sits in a file of the PR. A first review has no finding open, so `earlier` must be empty; results it still gives there, for findings an earlier round settled, are dropped and logged (`stale_earlier_ignored`) rather than failing the review. A second review must give each open finding exactly one result. A path the issue does not name is not reviewed, even if the repo's guides describe it; a PR that adds one is out of scope.
  - **Notes:** the splitter sizes all of a review's notes in one run. A `Small`, `two-way` note stays in the PR. Any other is reported to the queen, who parks it in `Technical debt` as a task of its own; code writes that task from the splitter's report and parks nothing else. A note the splitter could not size counts as too large. With the queen off, reports wait in the local log.
  - **Rounds:** a fresh worker process on the same branch and worktree fixes exactly the blockers and the notes that stayed, and nothing else. If nothing is left for it, there is no second review. A second review runs only if a code check sees a new head `SHA`, so waiting costs no tokens. It gives each item `fixed`, `not_fixed` or `partly_fixed`, judged from the code, and code drops anything new it reports, so the rounds end there. All fixed: the review is over and the PR is approved, which still means the merge gate below. A blocker not fixed, or a fix round that adds no commit, sends the task to `Blocked`. A queen's `retry` of such a task gives it one more fix round on the open blockers, with her note; that round's new head is reviewed again, and her retries cap how often this happens. The user's «Back to work» after a fix round that added no commit also gives one more fix round on the same head, because what held that round back, such as a blocker's merge, may be gone; if that round adds nothing too, the task is `Blocked` again until the next «Back to work». A note not fixed holds nothing and goes to the queen.
  - **Record:** each review is a PR comment with a hidden marker, and only comments by Kandu's own account count, so a restart loses nothing.
- **Merge danger:** the reviewer decides on its own whether a change is a **two-way door** (easy to undo) or a **one-way door** (hard to undo: data migrations, published APIs, sent messages), and states its blast radius. A one-way door waits for the user, even with `auto_merge` on. The user answers with the approve button on the dashboard's PR page, or by merging on GitHub.
- **Merge:** enforced in code, on the exact `SHA` that was reviewed. A new commit voids the review. If `auto_merge` is on, the supervisor merges only when all of this holds, then moves on to the next task:
  - the tests pass on that `SHA`, CI is not failing and the PR is not a draft
  - Only one merge test runs at a time for each project: a PR whose turn has not come waits with `another merge test of this project is running` and is tested in a later look (the next cycle), since slow tests time out when they share the machine. That wait is no failed test run and holds back nothing else. Projects never wait on each other's runs.
  - no blocker and no review thread is open, and every acceptance criterion is met
  - it is a two-way door
  - no companion PR is open and unreviewed. Whether a side is live cannot be told in code, so an unreviewed companion always waits
  - the project is not `frozen`

  These always wait for a yes, with a one-line question, and the queen answers them first (`approve`, below): a blocker answered without a code change, work deferred to a later PR, a thread resolved by someone other than its author, a risky area (auth, payments, data migrations) with no tests, and a one-way door. Default in this template: `auto_merge` **off**. The user turns it on per project once calibration (§15) shows Kandu decides as they would.
- **Base branch** ([kandu/base.py](kandu/base.py)): every part of Kandu that reads the branch a project works on asks one helper, which gives the project's `base_branch` or, when it names none, the repo's default branch. A worker's worktree starts from it and Kandu opens its PR against it; update rounds and the queen's rework merge it into the PR; the reviewer's and checker's diff, a checker's and the splitter's checkout, the deploy, the live check, the end-of-cycle check, a red `main`'s tests, Bazras's look, a Kanduban's worktree and the PR that offers a removed project's memory all use it. A project that names one tells its agents so in one fact line. Kandu never merges into another branch, and never merges the base branch into the default branch. **The merge guard:** a PR whose base (`baseRefName`, read from GitHub) is not the project's base branch is never merged, whatever `auto_merge`, the user's yes or the queen's yes says, and no update round brings anything into it: its merge waits with the reason "the PR's base is not the project's base branch", which the dashboard shows as waiting for the user's decision. **A missing base branch:** at the start of each cycle the supervisor asks GitHub whether each project that names a base branch has it in every repo. One that lacks it is held for the cycle as a paused project is: none of its tasks starts or goes on, and it is not sized or shown to the queen. The log records it once, when it is found missing (`base_missing`, with the branch and the repos) and when it is back (`base_found`), and the dashboard shows a notice that names the project, the branch and the repos until then. The doctor fails for that project too. A project that names no base branch is never asked: its default branch is always there.
- **Conflicts:** a reviewed PR that conflicts with its base gets an update round, unless a task under its `Blocked by` is still open: that task's merge moves the base again, so the round would buy nothing. The wait is then recorded as the merge gate records a merge held only by its blockers (`merge_held`), so later cycles skip the task, and the PR is updated once its last blocking task is merged. The user's yes, a one-way door or a question never hold an update: a yes holds for one head, and an update after it would void it. Kandu merges the base into the task's pushed branch itself (no rebase), in its worktree; work a run left uncommitted there is dropped, as it was never reviewed. Commits a run made but did not push, such as one cut off by a dropped connection, are first kept under `refs/kandu/kept/` in that copy, with an `unpushed_kept` decision that says where. Every merge commit carries a `Kandu-Run:` line. A clean merge Kandu pushes, with no agent (`base_merged`). A merge with conflicts is left open, and a worker gets only the list of files in conflict: it resolves them, keeping both sides, commits the merge, runs the tests and pushes. A pushed head that still holds a conflict marker in those files sends the task to `Blocked` with a PR comment, even when the round was cut short. So does a round that does not push the merge, with the worker's reason if it gave one. The new head is reviewed before any merge. An update round that pushes nothing new, a clean merge among them, leaves its own mark on that head, a PR comment by Kandu's own account (`kandu-update`), and the PR then waits: only this mark holds back another update round on that head. A fix round that pushes nothing leaves a different mark (`kandu-fix`), which holds back only a fix round, so a PR whose base moves after such a fix round still gets its update round; an update round's mark never counts as a fix try. Before the two rounds had their own marks, both wrote `kandu-fix`, so a PR with only those gets one more update round on that head.
- **Pushes GitHub shows late:** GitHub moves a branch at once but a PR's head a few seconds later. After a round Kandu reads the PR again until it shows the branch's last commit; one that still does not ends this cycle's turn of the task, so a push is never judged as no commit.
- **A fresh read:** each cycle reads a task's PR from GitHub before it drives the task, so a push made outside Kandu, or during a long cycle, is never judged on an old head. One case is not read again: a merge, or an update round, that waited only for open blockers (`merge_held`, with its head `SHA` and those blockers). While the copy shows the same head and the same open blockers, and the user dropped none of its blockers since, the cycle skips the task: no read from GitHub and no new `merge_waits`. The cycle's read of the repo brings a new commit or a closed blocker into the copy, and the next drive then reads the PR and checks the merge in full. A merge that waited for anything else is checked each cycle.
- **A closed issue:** a task whose issue was closed while its own PR is not merged stops at once. If another merged PR, or a commit on the default branch, closed it as completed, the task is replaced: Kandu closes its own PR with a comment naming the replacement and moves the card to `Done` (`replaced`). Closed by its own PR, the task lands as merged. Closed any other way, the task goes to `Blocked` (`issue_closed`), its PR is left as it is and the user is told at once: the queen cannot reopen an issue, so code refuses her rework and check on it. A `Ready` card whose issue is closed is never started and takes no worker's place in her `at_work`; the user hears of it once (`card_stuck`).
- **A merge GitHub refuses for a moment:** a refusal that passes by itself (5xx, a rate limit, the network) is tried again at once, up to three times, about 10, 30 and 60 seconds apart, each logged as `merge_retry` with its next try. A try that finds the PR already merged counts as merged, and the deploy follows. If those fail, the task stays in the cycle, taking no worker's place, and its merge is tried again about every minute until the cycle ends, on the same head with the checks it passed in this cycle; a new head is reviewed first. A read of the PR GitHub refuses for a moment on such a try counts as one more refusal: the merge waits for its next try. A yes from the user or the queen for that head, given after the refusal, tries it again at once. The cycle's end makes the refusal the task's one internal error of that cycle (Kandu's own trouble, §5), and the next cycle goes on the same way, so the user hears of it only after three cycles in a row. While Kandu retries it, her look lists the task under `waiting` with `next_try`, and code refuses her `ask_user` on it and an `approve` of a head she already approved, so nothing reaches the user. A refusal that does not pass by itself, such as a moved head, a conflict or a refused merge, is not tried again.
- **Tests that failed:** the gate runs a head's tests at most twice in a row. After the first failure it tests that head once more; after the second it records the wait (`tests_failed` twice, the reason «the tests failed twice on this head…») and runs nothing on that head in later cycles. A new commit is a new head and starts again with the same rule, and so does a recorded `tests_again_requested` for the head (the review page's «test again» control records it). While a head waits like this, code refuses the queen's `verify` for it and says why, so she cannot send checkers to re-run the same tests. Pause and freeze are unchanged.
- **The user's yes:** the approve button writes `user_approved` to the local log for one `SHA`, so a new commit voids it, and starts a cycle. It stands in for `auto_merge`, a one-way door and the review's questions. Every other condition above still holds: the tests run on that `SHA`, and a blocker or an unmet criterion still stops the merge.
- **Failed tests and «test again»:** the merge gate logs each run of the tests as `tests_passed` (head `SHA`, passed or not). The review page shows a head whose tests failed twice since the last request (what the gate counts as waiting; after one failure the gate retries by itself, so nothing shows) as waiting on failed tests, with the time of that run. «Test again» writes `tests_again_requested` for that `SHA` and starts a cycle, and the next merge gate tests the head again. It is offered only while the open PR's head is waiting like that and no request came after; any other PR gets `409`.
- **The queen's yes:** her `approve` writes `queen_approved` for one `SHA`, after code checks that it is the PR's head, that it was reviewed, and that no blocker is open and every criterion is met. On a project whose switch lets her, it answers the review's questions and the door, as the user's yes does, so a merge does not wait on the user for what she can judge from the code. It never stands in for `auto_merge`: a project the user merges by hand still waits for the user.
- **Whether her yes answers one-way merges** is a switch per project, «A hard-to-undo merge is answered by» in the project's settings pop-up, or `queen_answers_one_way` in the registry; it is off by default. Its choice is kept in Kandu's state, wins over the registry and is logged with the old and new value (`project_setting_changed`), as the split approval is (§2). While it is off, her yes answers neither a one-way door nor a question that waits for the user, from this head's review or an earlier one: such a merge waits for the user's yes, and code refuses her `approve` on a head that holds either. Her yes to a head that holds neither is kept, though it then changes nothing. Her look says, per project, whether her yes answers one-way merges. On the first cycle after the switch came, an install whose supervisor ran before sets it on in its state, once, for every project then registered, unless the dashboard already chose, and logs each (`project_setting_carried`), so those projects keep the behaviour they had; a new install and a project added later start off.
- **A red `main`** (`watch_main`, a project switch, off by default; «Hold the project when main's tests fail» in the settings pop-up, or `watch_main` in the registry; kept in Kandu's state like the other switches, winning over the registry, and logged). With it on, a PR whose tests fail in the merge gate makes Kandu run the project's tests on the current `main`, its base branch (§5) ([kandu/mainred.py](kandu/mainred.py)), and the result is kept for each `main` commit (`main_tested`), so one commit is tested at most twice. `main` is red only when two runs on one commit both fail (`main_red`); one failure and one pass count as passing. While it is red, every merge of the project waits with the reason "main's tests fail", before any test runs, and no task of the project starts from `Ready` except the fix task; runs at work finish their step. Kandu opens one High-priority Bug task for each red commit, naming the failing tests, puts it in `Ready` and never opens a second for the same commit (`main_fix_opened`); its own merge is not held, since its tests must pass on its head. The user is told once, by Telegram and on the dashboard, with the failing tests' names, for as long as `main` stays red: a later red commit keeps the first one's notice. The dashboard shows the project as red until `main` passes. Each cycle tests a red `main` again once its commit changed; a pass ends the red (`main_green`), new tasks start again, the dashboard stops showing the project as red, and the user is told once that `main` passes again. Then Kandu brings `main` into each open PR of that repo that had a merge check give "main's tests fail" while `main` was red (`mainred.waiting_for_update`): the PR's next drive runs the same update as for a conflict (`_update`: Kandu merges and pushes, a worker only resolves conflicts, so a conflict goes to the update round), once for each green (`main_updated`); the new head is reviewed and goes through the merge gate as usual, and a PR that did not wait is left alone. Off, none of this happens.
- **Deploy:** after merge, whoever merged, per the project's `deploy` setting, from the project's base branch in a separate checkout. Only this step gets all the project's secrets. A failed deploy sends the task to `Blocked`; nothing is reverted. A deploy that pulls into a live copy runs `<kandu>/.venv/bin/python -I <kandu>/kandu/pull.py <checkout>`: a pull that conflicts is aborted, so the live copy stays as it was and the deploy fails, instead of keeping conflict markers. A task in `Ready`, `In progress`, `In review` or `Blocked` whose PR someone merged takes the same path to `Done` in the next cycle, even when its issue is already closed; one in `Blocked` whose deploy or live check failed stays for a person. Landing a task closes its issue too, if it is still open: GitHub closes it from the PR's `Closes #N` only when the repo allows it, and an issue left open would hold every task it blocks.
- **"Done" means seen in the live software:** after deploy the supervisor opens the live version (screenshot or test) and checks that what the issue asked for is really there. Green tests alone are not enough.
- **End-of-cycle check:** after two or more merges in a project in one cycle, rerun its tests on the project's base branch, after its `setup` (§4), and request its live URL. The result goes in the event log as `project_checked`. A machine that does not answer, before the check or during it, gets none: that is `check_skipped`, and the user is not told, as a dropped connection says nothing of the project. A task whose step fails because the machine dropped the connection is tried again with no try counted.
- **No automatic revert.** `auto_revert: true` is refused by the config loader. If something breaks in the live software, the supervisor only reports it. The user decides.
- **Who may be trusted:** a worker uses the same GitHub account as Kandu, so it could write a review comment. The merge gate therefore reads the review from the local event log, and `gh pr merge --match-head-commit` makes GitHub refuse any other head.
- **Vague task:** no guessing. The task moves to `Needs info` and the user gets a question.
- **No hidden memory:** all state lives on the board and in issue comments. A cycle that is cut off resumes where it stopped, and progress is visible on the board at any time.

## 6. Rhythm — usage-based, not a fixed number of tasks
- A `systemd timer` wakes the supervisor every `wake_every_minutes` (default 60). A lock file prevents two supervisors running at once.
- Nothing for the queen to decide, no `Ready` task, or usage over a limit → sleep immediately, at no cost.
- Otherwise work until the tasks run out, or `max_cycle_minutes` (default 50) pass, or usage hits a limit, whichever comes first.
- **Limits** (`claude.limits`): 5-hour window % and weekly %. With a subscription shared with your own interactive sessions, leave a margin (example values: 70% and 60%). On a subscription, usage is read at no cost with `claude -p "/usage"`. A plan with no 5-hour window shows no session line; that counts as 0%, and the weekly line must still be there. Kandu also reads when each limit resets, on the machine's clock unless `/usage` names a zone, and keeps it in the dashboard's snapshot; a reset time it cannot read is left out and the percents still count.
- Usage is recorded per task, and reported per day and per project, so it is clear what each task cost and how much of the limit each project used.

## 7. Dashboard — Kandu's own
The user must be able to see exactly what is happening: the supervisor and every worker. The dashboard is part of Kandu, standalone, and **interactive**.
- **Supervisor state:** awake or asleep, next wake time, why the last cycle stopped; two usage bars (5-hour, weekly) with the limit lines. The user can change both limits there at any time; the next cycle uses them.
- **Claude login:** when the login expires on each machine Kandu uses, with days left. Read from `refreshTokenExpiresAt` in `~/.claude/.credentials.json` (only that field; tokens are never read into logs or state). The field is internal to Claude Code, so if it is missing the dashboard shows "unknown" instead of guessing.
- **Active workers:** task number, project, machine, phase (implement / test / review round N / merge / deploy / live check), elapsed time.
- **Live stream:** workers run with `--output-format stream-json`, so every file read, command and edit is logged and shown live, along with the reviewer's notes and the supervisor's decisions ("sent back because…").
- **Queue per project:** `Ready`, waiting for machine, `Needs info`, `Blocked`.
- **Done:** PR link, live link, screenshot of the final check, tokens used.
- **PR page:** for each review round, in plain words and with the brief in the page's language: the title, what the PR does, the result and a one-line recommendation, then each finding explained. The user can decide in seconds.
- **A merge held by another task:** a task whose merge waits only for tasks it is blocked by is not under "Your approval": it keeps its column, since no yes would merge it. Its card and its PR window show the latest reasons its merge waited, in the page's language, and each open task it is blocked by with its column; a split one shows its slices and the column of each. While one is open the PR window offers no approve button and says why, and the API refuses the yes. After a yes the window promises a merge in the next cycle only when nothing else still holds it; otherwise it names what does. A yes clears only the reasons it answers (a one-way door and the review's questions); the rest stay until the merge gate words its reasons again. All of it comes from the local log and Kandu's copy, with no GitHub call. It changes nothing about what holds a merge or when Kandu merges.
- **A machine that does not answer** shows at the top of the page: since when, and the tasks that wait for it, to be sized or worked. The supervisor keeps each outage in the log (`machine_down`, `machine_up`); a machine with an open outage is asked every cycle, so its return is seen even when no task needs it. Once it has not answered for `unreachable_alert_hours` while a task waits for it, the user hears once (`machine_unreachable`), and once more when it answers again.
- **A project at its daily token limit** starts nothing new until the next day (§6). The dashboard shows it in red: its patch in the meadow turns red with an outline a pause never draws, its card in the list says «Daily token limit reached» with today's tokens and the limit, and the legend explains the red while it shows. The state names each such project, counted as the supervisor counts it, so the mark goes by itself on a new day or a higher limit. It also gives every configured project its tokens today and its limit (`project_tokens`), counted the same way from the local log, with no GitHub call.
- **A task's status:** its card says in one sentence whether it is fine, has a problem, hit Kandu's own error, or is stuck, and why, read from the local log alone. Stuck means Kandu will not move it on by itself: a round that pushed nothing, a merge held after a yes or held twice in a row by something a fix answers, a task that stopped, or a loop stop. Only the user, the queen or a new head moves it. The meadow draws a stuck task on its way as «Stuck», unless an agent runs on it. The card also says what Kandu cleaned up in the task's folder before its last run (`worktree_cleaned`). A task that waits for the user says what it waits on, where, and the next step ([kandu/waits.py](kandu/waits.py)): the user's yes, a failing check (by name, with its log's link), an open blocker (with its issue), the user's decision (with what holds it), or a reason Kandu does not know. A failing check or an open blocker holds the merge whatever the user says, so then the yes is not offered as the step. This is worked out from the reasons Kandu records for a held merge, never from an agent's words: the merge gate names each failing check with its link, and a settled PR left to the user records the checks and blockers that hold it after `the user decides next`.
- **By day:** what was done on each day and how many tokens each task used, split by model and by worker, reviewer and supervisor. Tokens come from the `result` event of each run's `stream-json` output and are saved with the task. Above it, **Tokens by project** shows any range (today, this week Monday to Sunday, the last 7 days, this month, or any from–to): the total, each project with its tasks under it, most first, then «Kandu itself» (the queen, sizing, Bazras and the supervisor, work outside any task) and Didban with the free flights, so the rows add up to the total, with chips by role and model. Tokens are counted as the daily limit counts them, without cache reads; for today each project also says what counts against its daily limit, sizing included.
- **Controls from day one:** stop / resume the supervisor, stop one worker, pause / resume one project. Stop, from the dashboard in any look or `python -m kandu.supervisor stop`, kills no run: every worker, reviewer, sizer, inspector and queen run at work finishes its current step, and what it made is kept, a worker's push and its PR, a review, a size, a Bazras report. No new run, merge, deploy or end check starts, even for a task whose run just finished, and the queen's decisions from a look that was at work are recorded (`queen_held`) and carried out only on the first cycle after the resume. What happened after her held look, such as a task that finished while Kandu was stopping, is still news to her next look. Once the last run ends, the cycle ends with `stopped by the user`. While stopped, a wake from the timer or a yes on the dashboard starts no cycle; the stop is logged once. While runs still finish, every look says Kandu is stopping and how many bees are still at work (`stopping` in the state), then stopped. A resume while they finish lets the cycle go on as if Stop had not been pressed. Stopping one worker from its own button still kills that run at once, and the cycle's time limit and the usage limits still cut a running run off. A paused project keeps its board and tasks, and code keeps every agent away from it, the queen and the merge included, across cycles. A step already running finishes and nothing after it starts. `paused: true` in the config does the same and only a config change lifts it.
- **Config:** the dashboard takes a changed config at the next request, so a new project gets its own patch at once; a config with a problem leaves the last good one. A task the page cannot place gets a patch of its own, never another project's. **Wake the queen** starts a cycle at once, as the timer would. **Restart Kandu** writes the units again, so a new wake interval counts, and restarts the dashboard; a running cycle finishes.
- **GitHub use:** every `gh` call from Kandu, its agents and its sessions passes through `meter/gh`, which logs who made it and which hourly limit it counts against, never its arguments. Kandu's own GraphQL queries ask GitHub what they cost (`rateLimit { cost }`), so the meter counts the points GitHub took, not one a call. The dashboard samples the real limit every five minutes; `python -m kandu.ghmeter` puts the two side by side, so what spends the limit is measured, not guessed.
- **GitHub's back-off:** when GitHub refuses a call for a rate limit, primary or secondary, no Kandu process calls it again until GitHub's reset, or, when it gives none, a wait that starts at a minute and doubles with each refusal in a row, up to an hour (`state/gh/backoff.json`, [kandu/ghlimit.py](kandu/ghlimit.py)). Kandu's own calls fail at once while it lasts, as trouble that passes by itself, so a queued change waits and a task is tried again later; an agent's `gh` waits in `meter/gh` until then. The first call that goes through ends it. The dashboard's header says while GitHub refuses calls and when Kandu tries again.
- **Bazras:** a tab lists every project with a switch that turns Bazras on or off and the hour of its look, written to `projects.yaml`; below each, its recent reports, newest first, each marked all well or with its number of findings; a report with findings has a button that opens Didban on that project. Each project's card says when Bazras last looked and what it found.
- **Open requests:** a card lists the requests Didban keeps (§13), by project, and opening one shows its decision map with ✅ ❓ ⏳ ✂️, read-only; a request with no map says so. It reads only the request files in `state/`, so it costs GitHub nothing. A map is changed only in Didban. It ships off (`dashboard.show_requests: false`), and the user turns it on from its card.
- **Project settings:** the Settings tab follows the Kandu Clean design. The projects are a list in the registry's order, each with its name, its state line (the same as its lane on Today), a short summary (running or paused, its workers at most, its merge mode) and a button that opens its settings; «+ Add a project» opens the add flow (§1). A project's settings open in a **pop-up**, from the bottom on a phone and centred on a wide screen, with its name in a field at the top (renaming, §1) and every setting it has in three groups: work (running or paused, its workers at once and its priority, each with a minus and a plus, and its daily tokens), merge («Merges itself», `auto_merge`, and «Frozen») the queen (who accepts its splits, the user or the queen, §2, and who answers a hard-to-undo merge, §5), and **models**: for each of the worker, reviewer, splitter, live check and Bazras, the model the project names (§4), or the global one from `claude.models`, or Claude's default when neither names one, marked as coming from the global setting; a field takes a model and «Same as global» takes the project's own out. The queen's model is not there, as it is global only. A project paused in its config shows as paused and its pause cannot be changed, as only the config resumes it. Nothing changes until **Save**; Cancel, the close button or a tap outside it drop the changes. Turning «Merges itself» on asks first, and a no saves nothing; turning it off asks nothing. Save sends each changed setting through its own call with the dashboard's token, the same call each had before; one the server refuses keeps the pop-up open and says which and why, while the others are kept. Removing the project sits at the bottom, apart and marked as dangerous. Each change is logged with the project, the setting, the old value and the new one (`project_setting_changed`, or `parallel_changed` for workers). The pause and the two queen switches are kept in Kandu's state, so they survive a reload and win over the registry. The numbers, the merge mode and the models are the registry's own values: they are written in the project's entry in `projects.yaml`, line by line so its comments stay, after the whole config passes its check on a copy, so the file and the dashboard never disagree. The next cycle uses them. The meadow shows each project's merge mode beside its name (merges itself, waits for you, or frozen, which wins), and the mark, like the name, opens the project's pop-up. Beside the projects on a wide screen, below them on a phone: the **usage limits** at which new work holds, 5-hour and weekly, each with a minus and a plus by 5 up to 100 (`limits_changed`); the **machines**, each answering or not since when, with «Add», which opens the add flow at a new machine; and **Kandu itself**: its switches, each changing at once («Clean up after a merge», «Let the queen ask to drop blockers», «Show open requests»), its backup with «change», and **Kandu's pace**, which sets the workers at once in all of Kandu, how often the supervisor wakes and the longest cycle, in `kandu.yaml`'s `supervisor` block (`parallel_changed`, `pace_changed`); a new wake interval reaches the timer on «Restart Kandu». One switch for all of Kandu, «Clean up after a merge», turns the cleanup after a merge (§4) on or off; it writes `supervisor.clean_merged` in `kandu.yaml` and is logged (`clean_merged_changed`).
- **Backup:** a card shows whether the daily backup is on, its hour, how many copies there are and whether the last try failed; its dialog turns the backup on or off and sets its hour, folder and copies kept, written to `kandu.yaml`. Turning it on also starts its timer (§12).
- **Internal API:** the page reads and acts only through Kandu's own HTTP API (`/api/v1`), which covers state, tasks, tokens by day, an event stream and stop / resume. No outside system depends on it. To show the dashboard inside another app, that app's server proxies the page into a frame, so no new port opens. `docs/API.md` documents every endpoint and event with real examples, and tests check it against the code.
- **Requests:** an open page must not spend GitHub's hourly limit, which the whole account shares. All pages share one read of Kandu's copy, at most every 15 minutes, and a button, a finished task or a task moved on the copy reads it sooner, at most once a minute. Only the button reads GitHub into the copy first. A failed read keeps the last answer and waits 5 minutes. A hidden page asks for nothing.
- **Look:** a plain, modern page in `Vazirmatn`, which ships with Kandu, so Persian reads well and nothing loads from outside. In Persian every number the page writes uses Persian digits. Tasks are a group per project, which folds, is searchable and shows what needs the user first, so many projects stay readable. A click opens the task in its sheet, or a run in a dialog, instead of adding to the page. The token is asked for when a control first needs it. The meadow, folded at the bottom of Today, shows the hive: the queen is the oversight agent, each other agent is a bee (worker, reviewer, scout, splitter, inspector) with its own tool, the inspector circling the patch of the project Bazras is looking at, each task is a flower in its project's patch, the queen glows and speaks while she decides, and a task sent back from review shows a note. Every state of a task has its own flower and sign, a PR that waits for the user stands out most, the size of the flower is the size of the task, and marks under it show a hard-to-undo door, a return from review, a slice, a missing size, open questions, and a task that waits for the user's decision, which the task list marks too. That mark comes from the local log, and only a task still open in the copy carries it: its card on a board, not in `Done`, its issue not closed. ## 8. Notifications
- Only the important things: the supervisor stopped, something broke, a task is stuck and needs a decision, a usage limit was hit (which one: the 5-hour or weekly usage, the queen's daily tokens or a project's, and when it resets, or when Kandu looks again when `/usage` did not say), the Claude login expires soon (`claude.login_warn_days`, default 7) or has stopped working, and things of similar weight. Everything else only on the dashboard.
- The login check never calls `claude`, so the warning still goes out when Claude itself is down.
- `notify.events` lists what counts as important: `supervisor_stopped`, `failure`, `needs_decision`, `pr_ready`, `task_done`, `usage_limit`, `claude_login`, `machine_unreachable` (a machine has not answered for `supervisor.unreachable_alert_hours`, default 12, while tasks wait for it: one message per outage, and one when it answers again), `upstream` (the upstream check's behind or ahead count differs from the last good check's, or the check started failing; see the upstream check in §12). Default: all of them. The user turns each kind on or off from the dashboard: the Telegram button in Classic new's header opens a pop-up with a switch and an explanation for each, saved on Save, and Classic and Kandu Clean have the same switches in their Settings tab; the choice is written to `notify.events`, and the next cycle uses it.
- **Connecting Telegram from the dashboard:** the same places hold the bot's token and the chat ([kandu/telegram_bot.py](kandu/telegram_bot.py)). Each goes in a POST's body, never a URL, so no address or log holds it, and the dashboard refuses one in a URL. The token is checked with Telegram before it is written; both go to `local/.env` (mode 600) under the names in `notify.telegram`, and the next cycle reads them. The page learns only whether each is set, and the bot's name. "Find my chat" lists the chats that wrote to the bot since the dashboard started, and a press on one uses it. A test message shows both work.
- **Approving from Telegram** (`notify.telegram.buttons`, off by default, switched from the same places): the message about a PR that waits for the user's yes carries an Approve merge button. The dashboard takes the presses, by asking Telegram for them, so nothing on the brain listens to the internet. A press counts only from the chat in `local/.env`. Each button carries the reviewed head the message is about, its first 12 characters, never fewer. The first press names that head and asks once more; the second approves only that head, through the dashboard's own approval, so everything it refuses is refused here too, with its reason. A PR pushed to since the message is not approved from it, at either press: the user looks at it on the dashboard. Each press is in the event log as `telegram_pressed`, with its result. Each message opens with how soon the user must act: 🔴 stuck, 🟡 their turn, 🟢 done, ⚪ for information.
- The notifier is pluggable; Telegram is the first adapter. Messages are sent in `notify.language`, or in `language` when that is not set.
- The event log drives it ([kandu/notify.py](kandu/notify.py)). Each message is a fixed text, so no error or agent's words reach a third party. A message about a task that waits for the user adds what it waits on, where and the next step, as the dashboard says it (§7); a PR held by a failing check or an open blocker says so instead of asking for the yes. Only a check's name, cut to plain characters, and its https link come from outside Kandu. A state that lasts, such as a limit, is told once until it clears. A failed send never stops a cycle and shows on the dashboard as `notification_failed`.
- Every variable named `KANDU_*` stays with Kandu: `kandu/runner.py` removes them before it starts an agent or a project command, since a worker's code runs there.

## 9. Isolation — none in this version
Considered and deliberately left out of v1.

Note on the trade-off: a container does not by itself use more tokens, since token use depends on what the agent reads and does. The real cost is setup and upkeep: every tool has to be passed into the container (`gh`, SSH to other machines, deploy tools such as `wrangler`, a browser for screenshots, each project's secrets).

v1:
- No container, no separate OS user. Kandu runs as the user.
- A separate work folder for Kandu's clones, never mixed with the user's own working copies.
- Permissions live in the config, not in Kandu's code. `permissions` in `kandu.yaml` may give each role (worker, reviewer, splitter, live check, queen) an `allow` and a `deny` list. A role named there runs with `--permission-mode dontAsk`, so anything not allowed is refused. A role not named there may do everything (`--permission-mode bypassPermissions`): Bash, the network, SSH, secrets files. That is the default. [kandu/agents.py](kandu/agents.py) only fills in each run's branch (`{branch}`) and adds a project's own details: its test command and `allowed_tools` to a limited worker's list, its `forbidden` areas to every worker's deny list, and to every worker's deny list, limited or not, the commands only Kandu runs: `git merge`, `git pull`, `git rebase`, `gh pr create`, `gh pr edit` and `gh pr merge`. These rules match how a command starts, so they stop a worker's plain use of those commands, not one written another way, such as through `sh -c` or `gh api`. Every limited role may also run `bin/kandu-show`, which prints an issue or a PR from Kandu's copy (§3), and a limited reviewer may run `git diff`, so neither needs a rule in the config. A limited role of a project on another machine gets no read rule: it cannot reach `bin/kandu-show`, and its prompt holds the issue and the PR (§3). `config.example/kandu.example.yaml` holds a strict set to start from. `--setting-sources user` stays on every run, so a repo's own `.claude/settings.json` cannot change what a run may do. The same flag stops the repo's `CLAUDE.md` loading by itself, so the prompt tells an agent to search it for what its task needs.
- In the code, running a worker sits behind its own layer ([kandu/runner.py](kandu/runner.py)), so isolation can be added later by swapping only that layer.
- Each agent run and each run of a project's `test` is in its own systemd scope on its machine (`systemd-run --user --scope`). When the run ends, fails, times out or is stopped, Kandu stops that scope, so every process the run started ends with it: a dev server, a test browser, anything put in the background or detached. Over SSH this also ends a stopped agent at once. A deploy is not in a scope, because it may start what must keep running. A machine with no user systemd cannot give a run a scope: the run stays under the shell that starts it, named by the run, and when the run is stopped or cut off Kandu finds that shell and ends it with all it started. On Windows through Git Bash, where a dropped SSH connection ends nothing and Git Bash's own children leave no parent link Windows can follow, that shell first puts itself in a Windows job object that ends every process in it once the shell ends. A task has one agent run at a time: before an agent run of a task starts, Kandu ends any earlier run of the same task still going on its machine, as one a cycle that died leaves behind, and records it (`earlier_run_ended`).
- A machine may give each run a **run temporary folder** on its own disk (`run_tmp` and `run_tmp_dir` in its entry under `machines`), for a machine whose system temporary folder is small or in memory. It is off by default, and off, runs use the system temporary folder as before. On, each agent run, `test` and `setup` there gets a fresh folder `<run_tmp_dir>/kandu-<run>-<id>`, named like its scope, as `TMPDIR`, and an agent run as `CLAUDE_CODE_TMPDIR` too; locally and over SSH alike. The folder's `.kandu-run` file names the process that owns it. When the run ends, fails, times out or is stopped, Kandu removes the folder, after its scope. Before each run starts there, every `kandu-*` folder in `run_tmp_dir` older than a day whose owner is no longer running is removed: what a run left when Kandu itself was stopped or a connection dropped. Nothing else in the folder, and nothing in the system temporary folder, is touched. A deploy gets no run folder, as it gets no scope. The owner turns it on and sets the folder per machine from the dashboard's settings, in every look (`run_tmp_changed`), or with `kandu.add machine --run-tmp-dir`; `/kandu-setup` and `/kandu-add` ask about it for each new machine.
- A task's `Reference` may reach its runs as a **reference copy**, a read-only copy of a source in another project's repo (`supervisor.reference_copy`, off by default; the owner turns it on and off from the dashboard's settings in every look, `reference_copy_changed`, and `/kandu-setup` and `/kandu-config` ask about it). A task's `## Reference` section names a repo on a `Repo: owner/name` line and its paths as `code` words on the lines after it that start with `Path:` or `Paths:` or are list items. With the option on, before a worker or a reviewer starts, code reads the section and, for each repo that is a project in this install's registry (the task's own repo needs none), copies only the named paths: the files git tracks under them, from that project's copy on its machine, so nothing untracked, no symlink and no git folder, at most 20 MB. They go into a new folder of the run's own on the worker's machine (inside the machine's `run_tmp_dir` where that option is on, else its temporary directory), one subfolder per repo, with the write permission taken off. The worker's and reviewers' prompts say where it is and that it is read-only, and a role with an allow list may read that folder and nothing else outside its checkout; nothing from it is committed or pushed, and no agent may do more than read it. Kandu removes the folder when the run ends, however it ends: finished, failed, stopped or cut off by a dropped connection (a folder that a dropped connection leaves is a temporary folder like any other). A reference is refused, and the run goes on without it, when its repo is not in the registry, when its repo is private and the task's repo is public, or when its visibility cannot be read; a path that is not a plain path inside the repo is left out, a path the source does not have is skipped, and a source machine that does not answer or cannot be read means no copy. Each of these leaves one note on the task's issue, once per reason (`reference_note`): it says why and names no repo and no path, since the issue may be on a public repo. A run given a copy is logged (`reference_copied`).

If you want isolation now, two options:
- **Separate Linux user:** a `kandu` user that owns the work folder and only has access to the registered repos and their secrets. Simple, little overhead; isolation is only as good as file permissions.
- **Docker (or a devcontainer):** each worker in a container with only its project mounted. Strongest isolation; you must provide every tool and credential inside the container and keep the image up to date.

## 10. GitHub identity — the user's own account
- v1 pushes, opens PRs and merges with the user's own GitHub account (through `gh`).
- Everything Kandu does is marked: branch `kandu/<issue>-<slug>`, label `kandu`, and a `Kandu-Run:` line in the commit message, so Kandu's work is easy to tell apart in the history.
- If you want Kandu's work separated from your own: create a bot account or a GitHub App, give it a fine-grained token limited to the registered repos, and point `gh` for Kandu at that token. Repo rules that count PRs per author then stay unaffected by Kandu.

## 11. Safety rules
- An agent may do only what `permissions` in `kandu.yaml` allows its role; with nothing there, everything. Choose the rules before Kandu sees a project whose machine or secrets need them.
- Never touch an unregistered project, and never touch a user's own working copy.
- Never copy or log secret values.
- Never take external actions (sending email or messages, payments, paid services) without the user's approval.
- Never revert, force-push or delete branches other than its own `kandu/` branches.
- Respect each repo's own rules (CI, PR bots, protected branches).

## 12. Config and updates
- `local/` (gitignored) holds everything personal: `kandu.yaml`, `projects.yaml`, `.env` (secrets) and any personal notes.
- [config.example/](config.example/) has complete examples. `/kandu-setup` and `/kandu-add` write `local/` for you.
- **Recommended install:** a private repo of your own with this public repo as `upstream` and pushes to `upstream` disabled, so issues, PRs and mistakes stay private. A GitHub fork of a public repo cannot be private. Steps are in [README.md](README.md#recommended-run-kandu-from-your-own-private-copy).
- **Backup:** `local/` and `state/` hold what Git cannot rebuild: the config, the registry, the briefs, the project memory, the event log, the splits, the copy of GitHub and the flights. Once a day, at `backup.at` on the brain's clock, [kandu/backup.py](kandu/backup.py) writes both into one dated copy, `kandu-YYYY-MM-DD-HHMMSS.tar.gz`, in `backup.destination`, a folder on the brain's machine outside the two it copies. The run logs (`logs/`) are left out, and so are sockets and links. A copy is written under a temporary name and read back whole; only then does it take its dated name, and only then are copies past the newest `backup.keep` removed, oldest first. So a failed or partial backup removes its own temporary file and leaves every earlier copy as it was, and the newest good copy always stays. A failure is logged as `backup_failed`, with a reason that names no file's content, and told as a `failure` notification once a day; the timer tries again at its next wake. A copy holds `local/.env`, so the folder is readable only by its user and each copy only by its owner. `kandu-backup.timer` wakes every 15 minutes, like Bazras's, and does nothing while the backup is off or today's copy exists. The backup is off by default; it copies nothing off the machine and backs up no project. By hand: `.venv/bin/python -m kandu.backup now [--destination FOLDER]` makes a copy at once, even while off; `list` shows the copies; `restore COPY FOLDER` puts a copy's `local/` and `state/` into an empty folder, from which the user moves them into the install with Kandu stopped.
- **New features ship off.** Anything new that does work by itself, such as a timer, an agent or a daily look, is off by default, so an update never starts work nobody asked for. The user turns it on, and sets what it needs, in the dashboard, which writes the config; the config itself works too.
- **Version:** the repo's `VERSION` file holds Kandu's version, starting at `1.0.0`. [kandu/version.py](kandu/version.py) reads it from the install's own checkout, and `GET /state` reports it as `version` (null when the file is missing).
- **Cut a release:** the dashboard shows Kandu's version with «Cut a release» beside it, in every look: a stat tile in Kandu Clean and Classic, a chip in Classic new. A press runs `python -m kandu.release` (§12, its release command) in the install with no terminal, so it only proposes and changes nothing (`GET /release`), and shows in a dialog the proposed version, the changes and the changelog entry, saying that nothing has changed yet. Only the dialog's «Open the release PR», with the dashboard's token, is the yes (`POST /release`): the proposal is read again, and only when it is the one shown, by its fingerprint, does it run the command with `--yes`, then show the PR's link. When something reached `main` since, nothing opens and the dialog shows the new proposal to look at again. With no change since the last release the dialog says so and offers no confirm. Didban does the same on the user's word: it runs the command, shows what it printed, and runs it with `--yes` only on the user's yes to that proposal (§13). Nothing here tags or publishes.
- **Breaking mark:** a task is marked as a breaking change when it is defined, with `kandu.tasks --breaking`: its issue gets the `breaking` label, which the copy of GitHub shows at once. A task without the label is not breaking. The supervisor gives the task's PR the same label at each review round, beside `kandu`, so it is there before any merge and can be read back from the merged PR (`github.is_breaking`). A spec takes no mark, and the mark changes nothing about how a PR is reviewed or merged.
- **Release:** `.venv/bin/python -m kandu.release [--repo OWNER/NAME] [--yes]`, run by hand, proposes the next version from what reached `main` on the private copy (the `origin` remote unless `--repo` names it). The last release is the newest commit on `main` that changed `VERSION`; the one that brought in `1.0.0` is the start, so the first release counts from `1.0.0`. Every commit since is a change, read from its PR (`(#N)` in its subject): MAJOR when a change, its PR or the issue it closes, carries the breaking mark, else MINOR when that issue's `Kind` is `Feature`, else PATCH; a commit with no PR is a PATCH change. It prints the changes, the proposed version and the changelog entry, its changes grouped as Breaking, Features, Fixes (`Bug`) and Other. With no change it says so and proposes nothing. Then it asks; anything but a yes, or no terminal to ask on, changes nothing: no branch, file, push or PR. On a yes (or `--yes`) it makes the branch `release/VERSION` on GitHub at the `main` it read, writes the new `VERSION` and the entry at the top of `CHANGELOG.md` there, and opens a PR into `main`. The install's files are not touched, nothing is pushed to `main`, and it refuses a repo that is the `upstream` remote, so the public upstream gets only what the deploy pushes after the merge. Tagging and publishing are not done here.
- Updating Kandu is `git fetch upstream && git merge upstream/main` in the recommended install, and `git pull` in a plain clone. Nothing in `local/` is ever touched by an update.
- **Private guard:** `.githooks` checks new content, file names and commit messages against the private terms of the main working tree, at commit and again at push, because a cherry-pick or a rebase passes no commit hook. The push also checks each commit's author and committer, except a GitHub noreply address whose login is the name (`<id>+login@users.noreply.github.com`), which GitHub makes public by design; a term in the content or the message still blocks the push. The terms are the user's own words in `local/private-words.txt` plus those [kandu/privateterms.py](kandu/privateterms.py) takes from the setup itself: each project's name, family, repos, board owner and path, each machine and how it is reached, the brain's folders, Didban's sources and the values in `local/.env`. So a project added later is private from the moment it is in the registry, with no word written for it. The GitHub account, any term the public examples already use, and any term of the setup the user names in `local/public-words.txt` (such as a project named after an ordinary English word) are left out; only that exact term is, never its repo or path. If the terms cannot be read, every commit and push is blocked. `/kandu-task` checks a task on a public repo against the same terms. Text in a compressed file or in UTF-16 is not seen.
- **Upstream check:** with `upstream.enabled` on (off by default), the dashboard shows the install's `main` against `upstream.remote`/`upstream.branch`: «Up to date», «N behind», «N ahead», or both. [kandu/upstream.py](kandu/upstream.py) checks every `upstream.every_hours` (4 by default) and on «Check now»: it fetches that branch into its remote-tracking ref and counts, nothing more, so it costs no tokens and never changes `main`, a branch or a file of the install. A failed check shows «Could not check» with the time of the last good one, and the rest of the dashboard keeps working. «Ahead» counts only the install's own changes that `main` still holds: not merge commits, nor any commit from before `main`'s last commit whose files were exactly those of an upstream commit, so `main` with upstream's files is 0 ahead; one function counts it, the check logs it, and the dashboard and «Bring in updates» read it from the log. When a check's behind or ahead count differs from the last good check's, the user hears it once, in the notifications' language, with both counts and, when behind, to press «Bring in updates» on the dashboard (the `upstream` kind of notification). The first check ever and a check with the same counts send nothing. A failed check is told once, without git's reason, and no other failure is told until a check succeeds again. Both are read from the log, so a restart sends nothing twice. When `main` is behind, «Bring in updates», with the dashboard's token, creates one task on the board of `upstream.project`, Kandu's own project: bring the commits into `main` through a PR, keep the install's own changes where they conflict, except a change the install sent upstream and upstream merged, perhaps edited, where upstream's version is kept so `main` holds one version of it; keep the tests passing. While that task is open, a second press creates nothing and links to it. Nothing here merges or pushes: the updates arrive only through the task's PR and the user's yes.
- **Version badge:** in Kandu Clean, Classic and Classic new alike, the version badge sits in the header beside Kandu's mark and shows the install's version, from the `VERSION` file at the repo's root. With the upstream check on and `upstream.remote` on GitHub, [kandu/version.py](kandu/version.py) reads the upstream repo's newest release once a day, by the dashboard's own clock, a failed read too, and keeps it in the log (`release_read`, `release_read_failed`), so a restart reads nothing new; the page reads it from Kandu's state, never from GitHub, and runs no git: the clock works out the upstream repo from the remote and Kandu keeps it. Up to date, the badge says «latest»; behind, it names the newer version, and a click opens that release's changes on GitHub. Without an upstream, or after a failed read, it shows only the install's version and says the latest is not known, with when it last tried. On a phone it fits the header without scrolling sideways. Nothing here updates the install: updates come in only as in the upstream check above.
- **Upgrade notice:** when the install's `VERSION` is newer than the version the user last marked as read, every look (Kandu Clean, Classic and Classic new) shows a notice at the top of the page: «Kandu was upgraded to X.Y.Z», then the entry of each unread version in the install's `CHANGELOG.md`, newest first, as the changelog writes it, untranslated. A version is unread when it is newer than the read mark and not newer than the install; before the first mark, only the install's own version is. An unread version with no entry is left out, and with no changelog or no entry at all there is no notice. A version is linked to its release on the public upstream once published: the newest release the version badge's last read found, and each older version, which the deploy published before it. One «Mark as read» (`POST /upgrade/read`, with the dashboard's token) keeps the newest version shown in `state/version-read` and logs `upgrade_read`, so the notice is gone in every browser and after a restart, and comes back only when a newer version is installed. A deploy that does not change `VERSION` shows nothing new. Only the title and the button follow the dashboard's language. Nothing here notifies outside the dashboard, and nothing changes how a release is made, deployed or published.
- **Kandu as its own project:** an install may list Kandu's own repo, its private copy, in the registry, so a fix found in Didban becomes a task like any other. Its deploy pulls the merge into the live install and applies it as the dashboard's restart does, so the user sees it there first; it may then push `main` to the public `upstream`, and the private guard checks every commit of that push.
- **Tagging and publishing a release:** Kandu's own deploy runs `<kandu>/.venv/bin/python -m kandu.publish --install <kandu> [--remote upstream]` as its last step, after the change is live in the install and `main` is pushed to the public `upstream`. [kandu/publish.py](kandu/publish.py) takes a merge to be a release when the install's `VERSION` has an entry in its `CHANGELOG.md` (`## X.Y.Z - date`, up to the next entry), which only a release PR adds; any other merge creates no tag and no release. The tag, `vX.Y.Z`, goes on the last commit that changed `VERSION`, and only once that commit is in the install's checkout and in the upstream's `main`; otherwise nothing is tagged. Before anything goes public, the tag name and the entry are checked against the private guard's terms; a term found, or terms that cannot be read, stops the tag and the release, naming no term. Then the tag is pushed to the upstream, straight from the commit with no local tag, and a GitHub release named `Kandu X.Y.Z` with the entry as its text is created on the upstream's repo. A tag or a release that already exists is not made again, so a second run for the same release creates no duplicate, and a run that stopped after the tag only adds the release; a tag of the same name on another commit stops it. A release whose publishing failed is published by the next deploy that runs it. Any failure exits non-zero, so the deploy fails and the user is told; the merge stays.

## 13. Didban — control from your own machine
The brain runs on an always-on machine, which is usually not the machine the user sits at. **Didban** (Persian for "lookout", the one at the top of the tower) is how the user talks to Kandu from their own machine: one command opens a Claude Code session in a clone of this repo, in the control role. It is a role, not a service: no daemon, no new connection, nothing to keep running.

- **Taking requests:** this is Didban's main job. It says in one line what it understood and saves the request on the brain with `python -m kandu.intake`, so a closed session loses nothing, and the next session opens with what is not yet a task. After each round of refining, Didban saves the request's decision map with `python -m kandu.intake map ID --project PROJECT`, on stdin, naming the request's project once it is known so the dashboard can group it: one entry a line, each starting with ✅, ❓, ⏳ or ✂️. Code refuses a map in any other shape, saying which line is wrong. A new map replaces the earlier one, `kandu.intake list` shows each request with its map on one line, and the next session continues from it. The map is kept with the request in its private file, as `decided`, `asked`, `later` and `out` lists. A request leaves that list when its tasks exist or the user drops it. Didban does not follow a task after that: the queen and the dashboard do.
- **Reporting a session:** when a session ends, `didban` reads its transcript on the user's machine and sends the brain a summary: when, the session's title, tokens, and how many requests, tasks and answers it made. Code counts these, so a report costs no tokens. The dashboard shows them under daily usage, apart from the projects' limits. A window that was closed abruptly is reported the next time Didban opens, and a resumed session (`--continue`, `--resume`) is not reported.
- **Defining tasks:** a task is refined with the user first, and created only after the user says yes to its final text; naming a task is not that yes. `/kandu-task` then writes the issue directly with `gh`. The brain picks it up on its next wake, so this works even when the brain's machine is off.
- **Seeing state:** reads the boards from GitHub and live state from the HTTP API (§7) over SSH to the brain. Answers `Needs info` tasks from here.
- **Giving commands:** stop, resume and config changes (`/kandu-config`) run on the brain over SSH.
- **Knowledge:** project locations come from the registry. Other sources are listed in `didban.knowledge` in the brain's `kandu.yaml`. The role prompt tells Didban to read them there, on the machine that holds each one, read-only, and never to copy them.
- **Source of truth:** `local/` on the brain's machine. Didban reads and writes it over SSH, so there are never two diverging copies. The only local file is `local/didban.yaml`, which says how to reach the brain ([example](config.example/didban.example.yaml)). The list of sources is in `didban:` in the brain's `kandu.yaml`.
- **Limits:** it does not write code, does not change the knowledge sources it reads and keeps no memory of its own; all state stays on the board, or on the brain until a request is a task. `Edit`, `Write` and `NotebookEdit` are blocked in code. `Bash` stays open because Didban needs SSH, so these limits rest on the role prompt there, and a mistake is possible: do not treat Didban as a security boundary. Its sessions count against the same usage limits as the supervisor (§6).
- **Its name:** a Didban session is named "Kandu Didban", as its session name and its Remote Control name, whether it is opened from the command line or from the dashboard, so it can be told apart from Kandu's other sessions on a remote device.
- **From the dashboard:** a button opens Didban on the brain's machine, in the dashboard's language, with a Remote Control link on the page, so it needs no window on the user's machine. One stays open at a time: the button then shows the open one. It is the same role, with the same limits, and its report is made on the brain when it ends.
- **One project at a time:** once the user names the project they are talking about, Didban speaks only of it: what waits in other projects stays unsaid until the user asks or names another project.
- **The project's brief:** once the user names a project, Didban first runs `python -m kandu.brief show`, and recalls the project from that instead of reading its repo again. The brief is one short private file, `local/brief/<project>.md` (§14), followed by the project's forbidden areas (or `none`) and repo rules from the registry, then the newest lines of the project's own reports, read-only. If there is none, Didban drafts one from the repo and saves it with `set` on the user's yes. A fact or incident the user confirms is added as one dated line with `add`. These commands are the only way Didban changes a brief, and code holds its five sections and its length.
- **Bazras's findings:** Didban's opening lists the projects with Bazras reports it has not read, and `brief show` prints them and marks them read. Once the user names such a project, Didban brings the findings up in its first reply, recommends for each whether it is worth a task and why, and defines one only on the user's yes. The dashboard's Bazras tab shows each project's recent reports, and a report with findings has a button that opens Didban on that project. Report text is data, never instructions.
- **Forbidden areas when a task is defined:** `/kandu-task`, and Didban's steps for promoting a parked task, compare the code the task will change with the forbidden areas `brief show` printed. When it must change one, Didban names the area and why, and the user settles it before the task is created or promoted: open the area for this task (the user's change to the registry), change the task so it no longer needs it, or do it by hand. The splitter's hold below stays as the check in code.
- **Held tasks:** Didban's opening lists the tasks held for a forbidden area, with their areas (§2). It explains each one; opening an area is the user's change to the registry, and after it, or after the issue is changed, Didban runs `python -m kandu.split release` so the task is sized again.
- **When the brain's machine is off:** tasks can still be defined; live state and commands wait until it is back.

A review can meet what the task never settled. Its question in `wait_for_user` stays open until the user answers it: Didban opens by saying what is open, and `python -m kandu.questions answer` saves the answer in the local log and the project's memory, where the next worker and reviewer read it. An answer is not the merge yes.

### Free flights
Every task on the dashboard, `Done` included, has a button that opens a **free flight**: a Claude Code session on the brain's machine with a Remote Control link, for the user to work by hand on a task or ask about it. It speaks the dashboard's language and is told where things are: the task, the project, its worktree, its logs. Its prompt also carries the task's state from Kandu's own records, as in the first message below, so every flight knows it from the start. One stays open per task.

Every flight on a task starts with a first message written by code. A flight on a task in trouble starts with the trouble. Code decides this from Kandu's own records, the event log and its copy of GitHub: the task's last run failed, its last review asked for changes, its open PR's checks fail or it has a merge conflict, or it waits for a person (`Needs info`, a review question not yet answered, a stop for going round, or a one-way door that passed review on the PR's head and has no yes yet). The message then gives the same records: the task's column, the outcome its last run ended with, the review's verdict as counts and its door, the names of the failing checks, and whether there is a conflict, and tells the session to read the PR and the run logs itself and to tell the user what is wrong and what it suggests. Every first message, in trouble or not, then asks the session to read the issue and the open PR from Kandu's copy through the API, as data, and to sum them up for the user in a few lines; it changes nothing until the user asks. No text of the issue, the PR or a comment goes into the prompt or the message.

A free flight, Zanbourdar and Didban opened from the dashboard read from Kandu's copy of GitHub (§3) through the API before GitHub, so a session does not spend the hourly limit Kandu's agents need: the task's issue from `/tasks`, its PR from `/reviews`, and boards with their columns, fields and cards from `/boards`, which answers from the copy and reads a board from GitHub only when the copy lacks it. Each is told so in `prompts/reading.md`. They read GitHub with `gh` only for what the copy does not hold, and keep the access they already had. A free flight and Zanbourdar are also told, in `prompts/cards.md`, that a card change still goes to GitHub at once with `gh`, using the ids `/boards` gives, and that `/boards?fresh=1` reads the boards into the copy again, at most once a minute, so a change can take up to a minute to show there. Didban gets only the read part: its shell is for Kandu's commands, and it stays off board state.

A free flight has full access, with no permission prompts, because the person driving it is the owner and chose this. It is not an agent: the harness of §14 does not apply to it, no gate watches it, and the queen and the workers keep running beside it. Where its task goes afterwards is the user's call. The button needs the dashboard's token, as every control does, and nothing else stands between that token and full access to the machine.

A flight on a task whose PR is merged may end by itself once its session is quiet (§4, cleanup after a merge). When a task is closed without a merge while a flight opened before the close is still open, the user gets one 🟡 notification naming the task (`flight_left_open`, counted under `needs_decision`); the flight stays open, and the notification is not sent again.

Code sums up each flight when it ends, for a list under daily usage, apart from Didban's sessions. It counts against no project's limits, though it spends the same account's usage (§6). A flight on a task starts on its own with its first message, so it leaves its row with what it spent even if nobody spoke to it. A flight on a task whose issue is not closed in Kandu's copy of GitHub also closes by itself, on the sync's timer, after 12 hours with no activity in it. The sync never closes a flight on a closed issue. The cleanup after a merge ends one opened before the merge, the user is told of one opened before a close without a merge, as above, and one opened on an issue already closed, such as a `Blocked` task whose deploy failed, never ends by itself. It is summed up as one closed by hand. Didban and Zanbourdar never close this way.

Each session Kandu opens, Didban, Zanbourdar, a Kanduban or a flight on a task, from the dashboard or by a handoff with a first message, shows its Remote Control link once Kandu finds it: on the session's screen, in its tmux scrollback, or in its transcript, since a session that starts on a job at once scrolls the link off the screen. A session with no link after two minutes is ended and shown as failed, «the session's link did not come in time», only when it also shows no sign of starting: nothing written to its transcript since it started (read over SSH for a Kanduban on another machine). One that is alive and has written there is never ended for its link: the page shows it as open, with its close button and, until its link is found, no link, and keeps looking.

### Zanbourdar
Beside Didban, the dashboard's More menu has **Zanbourdar** (Persian for "beekeeper", the one who tends the hive itself): a Claude Code session on the brain's machine with a Remote Control link, tied to no task. It has full access, as a free flight does, and the same warnings hold: it is not an agent, no gate watches it, and only the dashboard's token stands before it. It starts in Kandu's live install and may change Kandu itself: on a branch in its own `git worktree`, brought into the install only as Kandu's `CLAUDE.md` says. Before it stops, restarts or reconfigures Kandu it says what that does to the work in hand and waits for the user's yes. One stays open at a time. Code sums it up when it ends, in the list of free flights.

**Handing a job to Zanbourdar.** Didban may hand Zanbourdar a job its own commands cannot do, and gets Zanbourdar's report back, through Kandu ([kandu/handoff.py](kandu/handoff.py)): the two run with different permissions, so a message from one session to the other would wait for an approval in Zanbourdar's session and expire unread. Didban writes the job, shows the user its text, and only on the user's yes to that text runs `python -m kandu.handoff job --language LANG` on the brain, the text on stdin. Kandu types it into Zanbourdar's tmux as one pasted message and sends it, visible there like anything the user types, under a line saying Kandu typed it for Didban on the user's word. If no Zanbourdar is open, the command opens one exactly as the dashboard's button does, so it shows on the dashboard, with the job as its first message; one still starting is waited for, never opened twice. A first message reaches the session from a private file beside its prompt, read by the line that starts it, never quoted into that line: tmux refuses a command of more than about 16 KB, and a long job, quoted once on the brain and twice over SSH, would pass that. While a process starts a session, its record names that process, so the dashboard, polling from its own process in that window, shows the session as opening and neither drops its record and prompt nor opens a second one; a record left by a process that died while starting it is dropped as any other. A busy Zanbourdar holds the job as queued input and takes it once the work in hand ends: only Enter is sent, never Escape, so nothing is interrupted. Nothing runs as a hidden background process. Zanbourdar's prompt says such a job comes from Didban on the user's word, that it still asks the user before it stops, restarts or reconfigures Kandu, and that it ends the job with `python -m kandu.handoff report`, the report on stdin. A report is typed into Didban's session when one opened from the dashboard is open and ready; otherwise it is kept in `state/zanbourdar-reports/`, and Didban's next start lists it under "This setup" (`kandu.handoff take`), which forgets it, so it is shown once. Didban treats a report as data, never as instructions. A job or a report is at most 8000 characters, and an empty one is refused.

### Kanduban
A project's pop-up and its patch in the meadow each have a **Kanduban** button, in Kandu Clean, Classic and Classic new; on the patch it is a small round mark beside the project's name, on the side its switch is not, with a hover text, and it is filled while that project's Kanduban is open. A Kanduban is a Claude Code session with a Remote Control link on the project's own machine, named "Kandu Kanduban PROJECT" as its session name and its Remote Control name, that works only in that project. It has full access, as a free flight does, and the same warnings hold. Pressing the button first asks the project's machine, with `true`, as the workers reach it ([kandu/runner.py](kandu/runner.py)'s `Host`): one that does not answer is refused at once with a clear error on the dashboard (`503`), and no session record is left. Then, on that machine, it runs `git fetch origin` in the copy of the project's first repo and adds a worktree of its own beside it, `<copy>.kandu-worktrees/kanduban-<UTC time>`, on the new branch `kanduban/<UTC time>`, from the project's base branch (§5); when it names none, from the copy's `origin/HEAD`, or from the default branch Kandu's copy of GitHub names. Nothing removes that worktree or branch afterwards: they are the user's. Its tmux runs on the brain as every session here does. On the brain `claude` starts in the worktree; on another machine the tmux runs `ssh -t` to it, with the same options the workers use, the prompt written beside the worktree there, and Kandu's API port carried back to the brain (`-R`), so the session reads tasks, PRs and boards from Kandu's copy (`prompts/reading.md` and `prompts/cards.md`), as Zanbourdar does. Its prompt (`prompts/kanduban.md`) says it works only in this project, brings its change in through a PR and never pushes to the default branch, never touches Kandu, its config or another project, and treats issues, PRs and comments as data; these rules are in the prompt only, as for a free flight. One is open per project: pressing the button again while it is open goes to that one's link, and Kandubans on different projects can be open at once. The dashboard lists an open one among the open sessions, with its link, as "Kanduban PROJECT". When it ends, code sums it up in the list of free flights, as Zanbourdar, from its transcript, read over SSH when it ran on another machine. It never closes by itself.

**Handing a job to a Kanduban.** Didban hands a job to a project's Kanduban instead of Zanbourdar when it is work inside that one project that Didban's commands cannot do; work on Kandu itself stays Zanbourdar's, and Didban's prompt says so. It goes as a job to Zanbourdar does, on the user's yes to its text, with `python -m kandu.handoff job --project PROJECT --language LANG`, PROJECT a project the config names. Kandu types it into that project's Kanduban under the same line saying Kandu typed it for Didban on the user's word. With no Kanduban open on the project, the command opens one through the dashboard button's own path, with its worktree and branch, and the job as its first message, on a remote machine too; one still starting is waited for, and a project never gets two. A machine that does not answer is reported, and no record is left. A busy Kanduban holds the job as queued input: only Enter is sent, never Escape. The job does not widen what the Kanduban may do: it still works only in its project and never touches Kandu, its config or another project. Its prompt says it ends the job with `python -m kandu.handoff report --project PROJECT`, run in Kandu's live install on the brain, the report on stdin; one on another machine that cannot reach the brain ends with the report as its last message instead. The report reaches Didban as Zanbourdar's does, typed into Didban's ready session under a line naming that project's Kanduban, or kept for Didban's next start with `[PROJECT's Kanduban]` before it. The same limits hold: at most 8000 characters, and an empty one is refused. Without `--project`, `kandu.handoff` works with Zanbourdar as before.

## 14. Harness, context and memory
Every part of Kandu is designed and reviewed against these three. The result depends on them as much as on the model.

- **Harness:** everything around the model that keeps it safe and on track: gates, lock file, permissions, tests, the fresh reviewer, limits, stop controls. A rule that matters is enforced in code, not only written in a prompt. Checks that need no judgment run without an LLM, so they cost nothing and still work when Claude is down. When an agent makes a mistake a fixed pattern could catch, the fix is an automated check, not a new line in a document; documents are for judgment calls.
- **Context:** each agent gets the smallest context that lets it do its job, and nothing else. A worker gets its issue and its project's facts, not the history of other tasks. A reviewer starts fresh. Project rules are checked at review, because the reviewer has the most room in its context and the worker the least. Prompts live in files, so they can be read, reviewed and improved, and they follow [docs/WRITING-PROMPTS.md](docs/WRITING-PROMPTS.md). Output that is not needed stays in logs, out of the model's context.
- **Memory:** nothing important lives only in a session. State is on the board, in issues and in state files. What is learned is saved as plain files per project in `local/`, read by the next worker and open to the user to correct. Memory is private: it never enters the public repo, and it holds facts and lessons, never secrets. An entry that proves wrong is removed. Each project's memory holds:
  - **Lessons:** what the next worker should know.
  - **Glossary:** one word for each project concept, so agents spend fewer tokens and name things the same way. Kandu's own is [GLOSSARY.md](GLOSSARY.md).
  - **Decisions:** one short paragraph for a choice that is hard to reverse, surprising without context and a real trade-off. Nothing else is worth recording.
  - **Rejected requests:** what the user said no to and why, so it is not proposed again.
  - **Do not flag:** what the reviewer must not report in this project: known contracts, intentional config, product decisions, and every wrong finding the user corrected. It is updated as soon as a correction happens.

Didban has its own memory of each project, apart from the above: the **brief** in `local/brief/<project>.md`. It holds what the project is, its main parts, the rules and dated decisions that shape tasks, the incidents (what broke and why), and where the project's own reports for Kandu live. It is read every Didban session, so code keeps it under a fixed length, and it changes only through `kandu.brief`. A project may also list `reports` in the registry: files on its machine, such as a lessons file in its repo, that `kandu.brief show` reads and never changes. Later a daily inspector writes there too.

## 15. Model review
Kandu must be able to show how well the model is doing, from its own records.

- Periodically (default weekly) a fresh-context reviewer goes through the tasks of that period and writes a report for the dashboard.
- Measures per model and task type: tokens per task, review rounds, tasks that reached `Blocked`, PRs the user corrected afterwards, and breakage seen after merge.
- It compares prompts and models over time, so it is clear whether a change helped.
- **Calibration:** every review round is logged, even with no findings, with what was offered, what the user kept and what they dropped. The target is about 100 PRs per project before full automation, and the measure is plain: the user would have made the same comments and merged without editing. This is the evidence for turning on `auto_merge`.
- It also looks at the environment, not only the model, and lists what would have prevented the problems it found, most severe first: an automated check that was missing, a rule the reviewer should enforce, a prompt line that changes nothing and can go, a fact the agent could not reach, a tool call that wasted tokens.
- It recommends; the user decides. It never changes a model, prompt or limit on its own.
