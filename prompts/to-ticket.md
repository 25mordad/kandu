# To ticket

Adapted from Matt Pocock's `to-tickets` skill (github.com/mattpocock/skills, MIT). The second half of `/kandu-to-issue`, after `prompts/to-spec.md` printed the spec's URL. What Matt calls a ticket is a task here. Ask the user nothing, as `prompts/to-spec.md` says.

1. Take the tasks of step 3 of `prompts/to-spec.md`, each with every field. Finish when every user story of the spec belongs to a task.
2. If the spec's `## Glossary` or an `(ADR)` decision holds anything, and the tasks do not yet hold it, add one task: "Record the glossary and decisions of spec #N". It adds each word to the project's `GLOSSARY.md`, in the form the file already uses, and each `(ADR)` decision to `docs/adr/` as `NNNN-slug.md`: one short paragraph of context, decision and why. One acceptance criterion names all the words, and one each ADR. It is a `Chore` of `Low` priority, blocked by nothing, done by an agent without tokens; its `Size` follows the scale of step 4 of `prompts/defining.md`. Finish when it is drafted, or the spec holds nothing to record.
3. Write each task as step 5 of `prompts/defining.md` says, from `prompts/templates/issue.md`, leaving `Out of scope` out: the spec's goes in. Finish when every task has its text.
4. Create them in order, each before any task that names it under `Blocked by`, so every name is a real issue: run the command of step 7 of `prompts/defining.md` with `--spec #N` and the task's fields, `--by-hand` and `--tokens` only for a task that has them. Finish when every task has printed its URL.
5. Run `.venv/bin/python -m kandu.intake close ID` on the brain for the request. Finish when it exits 0. Then show the user one table of what you created, the spec first and then each task in the order created, with its title, link, `Blocked by`, `Priority`, `Kind`, `Size`, `Deadline`, by hand and tokens; the spec has `-` for each field. Finish when the table holds the spec and every task.
