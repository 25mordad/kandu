# Defining a task

Turn what the user wants into issues a worker can finish, using `prompts/templates/issue.md`. `/kandu-task` and Didban both follow these steps. The quality rules are in DESIGN §2.

1. Find the project in `local/projects.yaml`. If it is not registered, stop and point to `/kandu-add`.
2. Read the project's brief with `.venv/bin/python -m kandu.brief show NAME` on the brain: it says what the project is, so read the repo only for what it leaves open. Read the open and closed issues. Check that the behavior does not already exist, and that `local/memory/<project>.md` does not list it as rejected. If it does, tell the user and stop. Then read the code the task touches, read-only on the machine the registry names, until you can name how it will be done, what it changes and what must stay out. Show the user this in plain words. It sets the criteria, `Out of scope` and the size, and it stays out of the issue.
   Then compare the code the task will change with the forbidden areas and repo rules `brief show` printed. When it must change a forbidden area, tell the user which area and why, and settle it before you create the task: open the area for this task (the user's change to the registry, not yours), change the task so it no longer needs the area, or do it by hand (`--by-hand`). Finish when the task needs no forbidden area, or the user has chosen.
3. Refine every task with the user in rounds, until no decision is open and nothing is silently assumed. The user may not be a software engineer: you bring the questions an engineer would ask, and they answer only what they can judge.
   - Before the first round, list the decisions the task holds: what it does in the usual case, at its limits and on failure, who may do it, what it keeps or changes, and whether it can be undone. What the code can answer, look up yourself: it is not a question.
   - Each round asks every question that can be decided now, numbered. A question that depends on another one's answer waits for a later round.
   - Each question has one line on why it matters, in what the user will see or lose, and a recommended answer. Say that "yes" accepts every recommendation, and that a number with another answer changes that one.
   - Ask about outcomes, in plain words. Make the technical choices yourself and state each as an assumption the user can reject.
   - After each round show the decision map, one short line per decision: ✅ decided, with the answer; ❓ asked now; ⏳ waits for an answer above; ✂️ out of scope.
   - Finish when the map holds no ❓ or ⏳ and the user has said yes to a short summary of the shared understanding: what the task does, the decisions, your assumptions and what is out of scope. A small, clear task has fewer rounds, but still ends on that yes.
   - A confirmed decision that will shape later tasks of the project is saved with `.venv/bin/python -m kandu.brief add NAME rules` on the brain, one English line on stdin through a quoted heredoc (`<<'END'`).
4. If the task is more than one slice, split it into issues, each delivering a complete path, and name the order in `Blocked by`.
   `Blocked by` names only a task this one cannot work or merge correctly without, never a related one: each name holds the merge until that task is done.
   Settle each task's fields in the same rounds: `Priority`, `Kind`, `Size` and a `Deadline` if it must be done by a date. The queen decides from these without reading the task, so getting them right is part of refining. `kandu.sizing` holds the scale: a `Small` task has up to 6 acceptance criteria and 18 changed files, a `Medium` one up to 10 and 36, and anything more is `Large`. Work that is hard to undo goes in a task of its own. A `Large` task does not go on the board: split it here, and `kandu.tasks` refuses it otherwise. The splitter still checks every size before the queen sees the task.
5. Write each issue in English, whatever language you and the user talk in: behavior instead of steps, no file paths or line numbers, and acceptance criteria that can each be checked alone.
6. Show the final text and create nothing until the user says yes to it. Naming a task, or saying what comes next, is not a yes.
7. Save the body to a temporary file and run `.venv/bin/python -m kandu.tasks --project NAME --title TITLE --body-file FILE --priority P --kind K --size S`, adding `--deadline YYYY-MM-DD` if there is one, `--repo` for a project with several repos, `--by-hand` if the user will do it themselves, and `--tokens` if the task must really call a service with the project's `task_tokens`. Building a feature takes no tokens: its tests mock the service. It sends the card's fields to GitHub before it returns. Finish when it prints the issue's URL. If it says the issue exists but is not on the board yet, run the same command with `--place URL` in place of `--title` and `--body-file`, never again without it: that makes a second issue.

A task the user chooses not to refine now is parked instead, only on their word: run `.venv/bin/python -m kandu.debt add --project NAME --title TITLE --body-file FILE`. It needs an English title and a short text, and steps 3 and 4 wait until Didban takes it up.
